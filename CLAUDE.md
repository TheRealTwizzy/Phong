# CLAUDE.md – Phong Project Guide

This document is the working guide to **Phong**, an arcade sports web app with a "blind half-court" mechanic and cross-device 2-phone multiplayer. It describes the code as it actually is — when the code and this file disagree, fix this file.

---

## 1. Project Overview & Core Concept

**Phong** reimagines Pong for mobile and desktop web. Each player sees only their own half of the court.

- **The Net Boundary**: the glowing top edge of the player's screen is the net.
- **Cross-Net Jump**: when the ball exits through the net, it leaves the player's screen and appears on the opponent's, travelling downward.
- **Knowing where they are**, in two tiers. The cheap tier is a pair of **net indicators** drawn on the court's own canvas: **Opponent**, a chevron that follows their paddle at all times, and **Ball**, a marker that appears only while the ball is on their half. Both are device preferences (`showOpponentIndicator`/`showBallIndicator`, on by default) and both are **ranked-legal**. The expensive tier is the **Opponent Sonar**, the mini radar that draws their half outright — their paddle and the live ball — which is a match RULE (`opponentSonar`, off by default), and switching it on **unranks the match** and suppresses both indicators for its duration. That is the trade: the whole game is a blind half-court, so a live mini-map of the half you are not allowed to see is not a presentation preference, it is the hardest rule in the game turned off; it still pays XP, and it costs the ladder. The suppression is derived per match, never written — the stored preferences come back by themselves the next time the sonar is off, and Settings shows the two rows off and disabled with the reason rather than reading as on while nothing is drawn. Solo reads the locally simulated half; a duel reads what the opponent's phone streams (`paddle_move` + `ball_pos`), so all three work identically in both. Note the frame convention: `oppPaddleXRef`/`oppBallRef` hold the SENDER's frame, and every consumer applies the head-to-head mirror itself. What the indicators replaced was ONE chevron labelled "OPPONENT IN PLAY" that actually tracked the mirrored BALL — it named one thing and drew another, and it went dark exactly when the opponent was most worth watching.
- **Physical 2-Phone Duel**: two phones placed top-to-top, connected by a 4-character code over WebSockets; the ball physically transitions between screens. That code is either the table's room id (an OPEN table) or its `joinKey` (a locked one) — `roomForCode` resolves both, and the lobby now hands out the four characters alone rather than a link or a QR (see §5). A `?room=CODE` deep link still **joins** rather than merely prefilling the code — held until the player has a username, so a first-time guest onboards and is then taken straight into the room. The lobby still renders its manual code box for the moment before `room_joined` lands, so a join is held in-flight until the server answers either way: a second `join_room` on the same socket is refused as "Room is already full", which would be about the room the player is in the middle of joining. Asking for a seat and being given one are separate moments, so the lobby can be dismissed in between: `room_joined` **and `room_created`** reopen it rather than seating the player behind a shut one — a guest left on a live court with no Ready control while the host waited for a readiness they could not signal, and a host left alone on one with no code to share and no Leave control while the relay went on holding the room. **Once a seat IS held, dismissing the lobby is leaving the room, and it asks first.** And when the HOST is the one who leaves, the guest goes too, and the room closes with them: `start_match` and `set_room_config` are refused to anyone but seat 0, and the host walking out ends the session the guest was invited into. Note what that sentence used to say — "seat 0 is only ever filled by `create_room`, so a hostless room can never have one again" — and why it had to be restated rather than deleted: a **pre-match `swap_seat` can fill seat 0**, so the host is now whoever holds it right now, and the two guards above already say exactly that and needed no edit. The room still dies with its host; there is simply no longer a claim that it *could not* be revived. The lobby deliberately does not bounce on `opponent_left`, but that rule is about a host going back to waiting for the next guest; for a guest it left them on a room that could not start, with nothing on screen to say so. **Holding a seat is not playing a match**: `room_created`/`room_joined` seat the player and leave them on the MENU with the lobby as a sheet over it, and `game_start` is the one thing that walks both phones onto the court. They used to flip the screen to `game` on seating, so a host picking a winning score stood on a live court with a ball waiting on them, and dismissing the sheet put them there with a working paddle, a serve the relay refused (`handleServe` needs an opponent) and a room the relay was still holding whose code they had probably already sent someone. The countdown effect needed no change — it fires when this player is on the court with the lobby out of the way, which `game_start` now does in one step — and a WATCHER follows the same rule: `table_state` seats them without a court, and `spectator_sync` walks them on only when it says a match is already under way. The matchmaking queue is the automated version of the same flow: the relay seats the pair, `queue_state: found` keeps the lobby shut for the one round trip, and its own `startMatch` produces the `game_start` that puts them on the court — so nobody sits on one waiting either. Both the X and the Leave button now route through one confirmation, and confirming runs the real `handleLeaveRoom` — `leave_room`, socket closed, court torn down, menu. Before a room exists there is nothing to leave and dismissing is just dismissing, which is also what keeps the in-flight-join window above working. **The link is also the one way into Phong that gets tapped from ANOTHER app**, so it routinely opens in a browser that is not the one holding the player's account, where the server cannot tell them from a first-time visitor: onboarding opens (which reads as being signed out) and their own username comes back taken, by themselves. Nothing can stop a foreign browser being a foreign browser, so the flow **says so and offers a way out**: on Android an `intent://` hand-off (`openInRealBrowserUrl`) genuinely opens the system default browser from inside a webview, and on iOS — which has no supported equivalent, `x-safari-https://` being undocumented and not something to build a lockout recovery on — the link goes to the clipboard to be pasted. Beyond that the modal **says so** — the modal explains that an account stays with the browser it was made in, and a taken name points at the restore door and opens it, instead of reading as a stranger holding your name. Every door out of that state used to be one-way; see §5. A socket the relay refuses for want of a live session is likewise **not** a verdict on the invitation: it re-mints and asks again on its own (larger) allowance, because three such refusals arrive inside a few milliseconds and used to eat the whole retry budget and kill the link in silence — and an invitation that genuinely runs out of attempts now says so rather than dropping the player on a menu that ate it.
- **Spectators**: a table has **four seats** — two playing, two watching, one beside each player — and whether the watching pair exists at all is `RoomMatchConfig.spectators`, a term of the match like the winning score rather than a `MatchRule` (a seat-availability flag in `MatchRules` would surface in the "what unranks this match" list as though it were physics). The **VENUE** overrules the host: `advanced`, `elite` and `pro` have no watching seats, and that is the whole spectator/ranked answer — a watcher sees the hidden half live with the sonar forced on and can describe it over a voice call, which is the sonar rule (§12) with a second person attached. Drawing the line by ROOM means no per-match flag, no `forceUnranked`, no new `unrankedReasons` case: a match in a room that permits watching rates exactly as it always did. Watching seats start **shut** on every table and the host opens them in the lobby. They used to open by default on a public table, on the reasoning that an advertised table is one where watching is part of the offer — true while public was one of two choices, and false the moment public became the only kind the client makes, because open seats force the match onto the RELAY (`rtc_signal` is refused for a watched table) and would therefore have taken the direct DataChannel away from every duel in the game. `scripts/e2e-venues.mjs` asserts the default directly, since `e2e-duel` prints its link badge without asserting it and a silently relay-only build passes there. `Room.spectators` is a **parallel array**, never a widened `players`: `players[0]`/`players[1]` and the `playerIndex === 0 ? 1 : 0` that falls out of them are load-bearing in every gameplay handler and in every function in `server/room.ts`, and a four-seat array would put a watching slot within reach of all of them. A socket's seat is one union (`{role:'player',index}` | `{role:'spectator',slot}`) rather than two nullables, because two nullables describe four states of which only three are legal — and the illegal one is the orphaned-seat bug class §5 records. The payoff is that every gameplay message is refused by a guard that was **already there**: `playerIndex()` is null for a watcher, so `paddle_move`, `point_scored`, `start_match`, `set_room_config` and above all `match_sync` — which can decide a match and trigger `recordRoomMatch` — close for free. `vacateSeat`'s spectator branch is an **early return, before the abandon computation**: all four clauses of `bothSeated && inPlay && !matchOver && currentPlayerId` are true of a watcher closing a tab mid-rally, so folded in as another `&&` it would write a real ranked LOSS to a player who did nothing (and `persistDuelStreaks` would not save you — its own guard is `!inPlay || matchOver`, so mid-rally it runs). On the wire a watcher is made to look **exactly like the player beside them** — `opponent_paddle`, `opponent_ball`, `ball_incoming` and `score_update` arrive byte-identically — so App's existing handlers need no spectating branch; the only new frames are `watched_paddle`/`watched_ball`/`watched_ball_left`, about that player's OWN court, and their rule is **raw, no transform**, which is the likeliest bug in the feature and invisible against a symmetric fixture (a paddle at 0.5 looks right either way). A **watched table is a RELAYED table**: `rtc_signal` is refused while the seats are open, because a P2P match never reaches the relay at all and a watcher would sit in front of a frozen court — the client declines to offer, but the relay is the only signaling path and is what a modified client cannot get past. `spectator_sync` is the easy one to forget: somebody sitting down at 3-2 has missed `game_start` and every `score_update` since. Watching is **ungated** — the bracket gates who PLAYS — and standing up costs nothing, so it raises no confirmation and returns to the room's table browser rather than the menu. **Seats swap, pre-match only**: `swap_seat` is always a MOVE to an empty chair, never an exchange with somebody who did not ask, and any move touching a *playing* seat is refused once `matchSeq > 0 && !matchOver` — deliberately stricter than `set_room_config`'s `!inPlay || matchOver` by exactly the countdown window, since `startRatings` is sampled by then, and because "stand up, look at the hidden half, sit back down" is a two-second cheat in a game whose whole premise is the blind half-court. A watcher moving 2↔3 is exempt and re-seeded with a fresh `spectator_sync`. A swap that would leave nobody playing is refused: `leave_room` is the only way to empty a court and it is judged as an abandon. The vacated playing seat is **cleared** (`clearSeatStreaks`) rather than persisted — a run belongs to a player, not to a chair, and `startMatchStreaks` opens `bestStreaks` ON `streaks`, so a value left behind becomes the next occupant's opening PEAK, which is permanent. `soloSince` is **untouched** by a watcher arriving and maintained with `?? Date.now()` on a swap, or a lone host could park a table forever by having a friend sit down, or by swapping 0↔1; `lastActive` is never written by a swap at all. `isRoomEmpty` needed no change and its doc did: "empty" now means no live PLAYER, so a table watched by two people and played by nobody is swept within 15 seconds — the brief's "no empty tables in the database" for free.
- **Solo AI**: an adaptive AI opponent (Rookie / Pro / Elite / Cyber / Chaos) on the hidden half. Each difficulty is a *rating*, not a fixed parameter set, and slides part-way toward the player's own skill — see §7. Each rung simulates a band of the PvP ladder: Rookie plays like an Unranked/Contender human, Pro like Vanguard/Ace, Elite like Master/Grandmaster, Cyber like Grandmaster/Legend, Chaos like Legend+.
- **Practice Wall**: fully solo drill mode — no opponent exists and the ball never leaves the player's screen; the net line acts as a *return line* that bounces every ball back. HUD shows current/best return streak. Counts no match and moves no rating, but banks thin streak-scaled XP on exit (`practiceXp`, server-computed, capped per UTC day) so every mode is progression — and leaves a **history-only session row** in `matches` (mode `practice`, unranked, the session's peak on the rally column, synthetic opponent `wall` that is never a tap target) so the Practice Wall has a timeline like every other mode; a visit where no ball was returned records nothing.
- **Split Screen**: local 2-player classic Pong on ONE device (`SplitScreenMatch`) — full court on a single screen, net across the middle, one player per half (multi-touch; each pointer is locked to the half it started in). No networking, unranked, and nothing written to any profile — the two sides' rally streaks are tracked separately and live only for the match, because only one of the two people at that phone has an account.

**Navigation**: the app opens on a **MainMenu** screen (`screen: 'menu' | 'game'` in `App.tsx`). **The menu is a PLACE, not a list of modes** (`src/venues.ts`): a player walks into a **BUILDING** — `SOLO AI`, `PVP` or `TRAINING` — and then picks a **ROOM** inside it, which is where the match actually begins. There is still no router and still only two screens. The buildings are a **tab strip**, the same shape and the same markup as the Match History and Leaderboard filters (`role="tablist"`, selection exposed as `data-selected`, never as a class), with the chosen building's rooms listed beneath it. A strip rather than a drill-down for two reasons: switching buildings is one tap instead of back-then-tap, and — the one that bit — there is then no navigation state a player can be stranded in. **A room a player cannot enter is folded away**, and the selected tab is the fold: tapping the tab you are already on opens the locked rooms, tapping it again — or moving to another building — closes them. A list is a list of places you can go, and five rows of padlock is a wall rather than a menu; the rungs above are still worth SEEING, which is what the fold is for, and the tab carries a lock-and-count chip so the toggle is findable at all. **A locked row is readable rather than merely shut**: it names the achievement that opens it, and its lock is a TAP TARGET — the `LockBadge`/`UnlockHintSheet` pair the winning-score picker already uses, which was written for this call site and never wired to it (`LockBadgeProps.id` documents `'room-ai_pro-lock'`, the room list's id scheme and not the segmented control's). The tap reveals that achievement's own description, which is the only place a gate is ever stated in words. A row can show a trophy NAME and nothing more, and `🔒 Machine Ender` is not something a player can act on; the requirement behind it — "Beat the Cyber AI 10 times. Needs Grandmaster tier or above." — was three moves away, off the menu, onto the TROPHIES page and into the Ladder branch, and a `title` attribute does not exist on touch, which is the only input this game has. So the reason a rung was shut lived where the player had no reason to look. Rendering the description on the row instead was rejected: `Achievement.title` and `.description` are hardcoded English in `src/achievements.ts` and are not `t()` keys, so inline prose would have put English on every locked row beside a localized PvP lock line — behind a tap it is opt-in, and the overlay's own `locked` label is the one genuinely new string. The button stays honestly `disabled` and keeps `#room-{id}`: `e2e-venues` reads `data-locked` off it and `e2e-achievements` reads `el.disabled`, which on a `<div>` is `undefined`, so an id that drifted onto the wrapper would make every "should be locked" assertion in that suite pass **vacuously** — green, and testing nothing. The tap target is therefore a SIBLING overlay inside a `relative shrink-0` wrapper, which is the `shrink-0` rule above paid one level up. A PVP lock needs none of this: `lockReason()` already resolves the verdict into a localized sentence naming the level or the tier. Note the consequence for anything that drives the menu: `#building-solo` is the DEFAULT selected tab, so a tap on it is no longer a no-op selection but a reveal toggle. A drill-down version shipped first and broke four browser suites on the same shape: a helper walked into the Solo building to set a match length, closed the sheet, and left the menu inside that building, so the next `#building-pvp` tap found nothing. The menu now always has a building selected (`DEFAULT_BUILDING`, Solo — the one a player alone with one phone can start right now), so there is nowhere to be that is not in one. Solo rooms carry no description line: the rung's NAME and the win-chance beside it are what a player picks on, and a sentence of prose under each of five rows was five sentences to scroll past. **A SOLO room IS a rung of the AI ladder**, so entering one sets the difficulty and the pre-match sheet then *confirms* it rather than asking a second time — one answer, given once, in the place the player gave it; the picker that used to sit in the sheet is now that room list. **A PVP room is a skill bracket**, gated on level and visible tier at BOTH ends (a Legend may not drop into BEGINNER — a bracket with only a floor is one a veteran farms), and the brackets deliberately overlap at their edges so a rating that wobbles across a floor never strands anybody. **CASUAL is the one that does not move the ladder** (`RoomDef.ranked`, see §7): ungated, open to everyone, XP and hidden MMR but no visible tier — which is what its own description has promised in seven locales since it shipped while the server rated it like any other bracket. **TRAINING** holds the Practice Wall and Split Screen, which gate on nothing because there is no opponent to rate against. `roomEntryVerdict()` is the one predicate the menu's lock and the relay's refusal both ask, so they cannot drift — the menu is the client, so a bracket it draws is a bracket the server has to enforce, exactly as `DIFFICULTY_LOCKED` is enforced behind `/api/match/record` rather than trusted to the picker. An UNPLACED player (everybody, until five ranked games) sits below every floor and is deliberately not *also* excluded by a ceiling: they belong in the ungated rooms rather than being refused at both ends. **Every mode opens the same pre-match surface**: a duel opens the lobby, and the other three open a pre-match `Sheet` — header, scrolling body of match settings, Start CTA pinned in a footer. They used to expand into the menu list as an accordion instead, and that was a broken flow, not just a second one: the scroll region is a flex column, the accordion card carried `overflow-hidden`, and a flex item whose overflow is not `visible` has an automatic minimum size of **zero**, so the column squashed its children rather than overflowing. Nothing overflowed, so nothing scrolled; the other mode rows collapsed to ~12px slivers; and the Start button, last in a clipped card, sat ~160px below the viewport where no gesture could reach it — which is why *editing a match setting* read as *this mode cannot be started*. **Every child of that scroll region is `shrink-0`**, which is what stops the collapse returning. Match settings — AI difficulty and winning score — are locked in on that sheet **before** a solo match starts, and in the **lobby** before a duel (the host sets them, the guest reads them); neither is editable once play begins; the in-game Settings modal carries device/presentation preferences only. The in-match HUD keeps just sound/reset/settings/home; the winner overlay offers Play Again (or Rematch) and Main Menu. **Reset and Play Again are the same intent** — restart this match — so both leave the rally run exactly where it stands: a restart is not a miss, so an unbroken run is not confiscated, and neither is it a fresh look at the stored carry, which would resurrect a run already missed away. **The MATCH, though, ends there**: quitting to the menu or pressing Reset in a solo match a point has been scored in records it as a loss (`abandoningLiveSoloMatch` → the ordinary `recordMatchCompletion(false)`), the same way the relay records a walked-out duel. **Every route out of a live match therefore goes through ONE confirmation** (`exitConfirm`, `'duel' | 'solo-quit' | 'solo-reset'`), and it names the consequence rather than asking "are you sure": the loss, the opponent's win in a duel, and whether the ladder is on the line — that last read from `unrankedReasons`, the same verdict the pre-match sheet shows, so a Rookie, sonar or Casual-table match is not threatened with a rank it was never going to move. The routes that cost nothing never raise it: a finished match's Main Menu, the Practice Wall, a lobby with no match in it, and a solo match still at 0-0. Without it a player who quit every solo match they were behind in recorded only their wins — half of the reported "100% win rate, no losses" — and Reset would have been the free version of the same escape. At 0-0 nothing has happened yet and backing out costs nothing.

**The menu screen holds five PAGES in a closed loop.** There is still no router and still only two SCREENS; the pages are a second axis of navigation on the menu one. `PLAY · RANKS · TROPHIES · HISTORY · SETTINGS` sit in a pager between the fixed header and the fixed tab bar — a drag tracks the finger 1:1 and settles to the nearest page on release, a tab tap jumps without a slide, and the loop wraps at both ends: a finger moving LEFT brings the next page in from the right, so `PLAY` dragged rightward wraps back to `SETTINGS`. Browser Back is deliberately **not** wired to it. What that replaced was a tab bar that named five destinations and had one: `const current = !tab.onClick` defined *the current tab* as **the tab with no handler**, so `PLAY` was permanently accented, permanently `aria-current="page"` and a dead button that did nothing when tapped, while the other four flipped a boolean in `App.tsx` and opened a `Sheet` OVER the menu — navigating read as stacking rather than as going somewhere, and the bar's own selected state was a side effect of a missing callback rather than a fact anything could query. It is now `i === pageIndex` and every tab has a handler. The pager mounts **three slots, never five** — `prev`, `current`, `next`, with `wrapIndex` closing the loop arithmetically — because the other way to make a strip endless is to clone its edge pages, and in a repo where every browser assertion is an `#id` a clone puts a second element carrying each one into the document. A page that leaves that window unmounts and its view state resets, which is the intended "fresh page on arrival"; the page that STAYS in it is the other half of that sentence, and it had to be built. **Fresh on arrival is right for a page and wrong for a METER**, which is why the two progression meters are not on a page at all — see the header pill below. **Every page refetches when it becomes CURRENT** (`useArrivalRefetch`), because a mounted page's fetch effect fires when it becomes a NEIGHBOUR and never again — so leaving the menu on `PLAY` and swiping to `RANKS` ten minutes later served the board as it stood the moment `RANKS` slid into the window, and `TROPHIES` and `HISTORY` had it identically. The mount-time fetch for a page one swipe away is **kept**: it is what makes a dragged-to page show content instead of a spinner, which is also why the obvious remedy — gate the fetch on being current — is worse than the bug it fixes, since the incoming page is not current until the settle, so a drag toward `RANKS` would slide an empty panel in and fill it afterwards. Staleness traded for a blank, and the blank is worse. Arriving is not a new concept either: `RanksPage` and `HistoryPage` spend the `reloadKey` their own refresh button already owns, and the tree, which has no refresh button (a real inconsistency, deliberately left), keeps the counter inline rather than earning a `TrophiesPage` wrapper that would hold nothing else. **The prerequisite is that a refetch never blanks what is on screen** — `isLoading && list.length === 0`, the rule `MatchHistoryList` had all along and the other two did not; without it every arrival trades staleness for a flash, and it fixes switching leaderboard category and toggling bots for free, which threw the rows away and rebuilt them for the same reason. The arrival guard compares the previous VALUE and never counts runs, because `main.tsx` renders under `StrictMode` and an effect therefore runs setup → cleanup → setup on mount: a first-run flag is spent by the first setup and fires on the second, which is a double fetch on every mount, in dev only, where nobody would look. `pages` is four render functions rather than four elements for exactly this — a page has to be told whether it is the one on screen, which stopped being the same question as "am I mounted" the moment the window held three slots. The two off-screen pages are `inert`, or a Playwright click succeeds on a button one viewport away and a suite passes on a broken pager. **`#menu-pager` declares no `touch-action` at all**, deliberately: an ancestor's restriction cannot be widened by a descendant, so `none` or `pan-x` there would withdraw vertical panning from every `scroll-y` inside every page — with no build error, no red test, and nothing to see but scrolling that had stopped working. The pages carry their own `pan-y`, and the TAB BAR carries an explicit one — the same declaration being right in one place and wrong in the other, which is exactly why the reason has to travel with it. Right on the bar: it advertises a swipe, at the default `auto` the browser may claim a horizontal drag and answer with `pointercancel`, and the handler reads a cancel as *not a page turn* — so the advertised gesture works under a mouse and fails under a thumb — while nothing inside the bar scrolls, so reserving horizontal there costs nothing. Wrong on the pager: it is an ancestor of `AchievementsTree`'s `scroll-x` branch strip, whose own `pan-x` would simply stop applying. **A page change fires on `pointerup` and never on `pointercancel`**, which is `CourtCanvas`'s serve rule one level up: a cancel is the browser saying it has taken the gesture, and a menu that turns its own page while the player is opening a notification shade is the same bug that used to fire a serve.

Two defects in that gesture were **invisible to mouse input**, which is the part worth remembering the next time anything here grows a pointer gesture over ordinary DOM. `getCoalescedEvents()` returns an EMPTY ARRAY for an event that coalesced nothing, and `[] ?? fallback` does not fall back, because `[]` is not nullish — the sample loop ran over nothing, the axis never locked, and the gesture was dead under a finger while every mouse leg of `e2e-menu` passed. And `setPointerCapture` was killing the drag it had just claimed: a touch pointer is IMPLICITLY captured to the element it went down on, so taking capture TRANSFERS it, which fires a bubbling `lostpointercapture` straight back into the handler that tears the drag down. Capture is mouse-only now — a mouse has no implicit capture and genuinely needs one, touch already has one and can only lose by being given another. `CourtCanvas` and `SplitScreenMatch` both capture on `pointerdown` and are right to, because they are `touch-none` canvases with no competing scroller and no inner button whose `click` the capture would retarget; **that reason does not transfer to a pager over real elements**, and copying the pattern is what broke this. The thresholds themselves live in `src/gestures.ts` and are pinned only by `tests/gestures.test.ts`, because this environment cannot observe `touch-action` at all: CDP's `Input.dispatchTouchEvent` injects downstream of the compositor hit-test that enforces it, and scrolled a `touch-action: none` element 348px in a three-case probe built so that a null result could not be mistaken for a broken harness. `scripts/e2e-menu.mjs` says so in its header rather than implying a coverage it does not have. The same division is why the release VELOCITY is computed there and not in the hook: `pageSettle` had always documented that its caller must zero a stale reading, and the caller was the one place in this repo with no layer able to say so. It measured its ~100ms window from the newest SAMPLE rather than from the release — and a finger held still fires no `pointermove` at all, so the trail stops growing and goes on reporting the flick that ended it. Flick hard, rest for two seconds, lift, and a drag that never came near the distance threshold turned the page. `trailVelocity(trail, now)` states it where a test can hold it.

**The header pill is the progression readout, and it is in the header because a meter must not be fresh on arrival.** The capsule reads `username · rank · level` over the rank meter and the XP meter, stacked; what that replaced was the pill showing username and level alone, above a full-width rank card that OPENED the PLAY page and said the same three things a second time — a 72px rank ring, the level again, the daily streak and the XP bar, about a fifth of the page before a player reached the quick-match row. The ring is a bar now for two reasons beyond the space: its arc was a hand-rolled `transition: stroke-dashoffset` that bypassed `useMotion()`, making it the one meter in the app that ignored `prefers-reduced-motion`; and a round line cap draws a blob of its own width at each end, so an arc shorter than the cap was ALL cap — at a tier floor the meter rendered as a detached cyan dot beside the badge with no ring to explain it, which is what it was reported as. A `scaleX` fill has no cap and draws a floor value as a hairline, so do not put the ring back without solving both again. Being in the header is what fixes the animation: it is the one region outside `#menu-pager`, so a page turn no longer unmounts either meter — and the remaining unmount, `AnimatePresence` taking the whole menu away for the length of a match, is exactly the moment the value HAS changed and the movement is the thing worth showing. So `ProgressBar` grew an opt-in `resumeKey` and `src/components/ui/meterMemory.ts` remembers where each keyed bar last stood; without it a player who had just earned XP came back to a bar filling from EMPTY, which reads as the level being earned a second time rather than as the meter moving. The key names a **band** and not a meter (`menu-xp:{level}`, `rank:{tier}`) because XP into a level runs to 0.95 and the next level opens at 0.05: resumed from the old band, gaining a level would animate as a long slide leftward. Two mounted bars must never share a key, each would write the other's origin; the store is module scope and deliberately NOT persisted, since a reload has no last position and a bar that arrived already full would be lying about continuity. Three sizes are measured rather than guessed and all three are load-bearing. The capsule's inner column is three rows in the 30px its avatar sets — a 14px chip row, a 2px gap, the 4px rank meter, another 2px gap, the 4px XP meter — because `pt-safe-bar` offsets the toast stack by `pt-safe + 48px` to clear both top bars and this header is ALREADY exactly that. A taller capsule fails no build and reddens no test; it just puts every toast over the header the offset exists to clear. That is not a hypothetical: the first build of the three-row version stood at **60.09px against a 60px offset**, because the tier chip's own `py-0.5` made the column 30.1px — sub-pixel, invisible, and caught only by the height assertion in `e2e-menu`. `TierBadge` grew an `xs` size to spend that padding, and the slack came from the chip rather than from the gaps between the meters deliberately: two 4px bars need the 2px between them to read as two. The tier chip is capped at 8rem because at `text-2xs` the widest labels are "Cyber Overlord" at 128px and "Grandmaster" at 109px, and a cap under either truncates a rank for every player who holds it however much room the row has, since `max-w` does not yield when there is space. And the username carries a `min-w`, because a flex item at `basis: 0%` absorbs none of the overflow — without it the badge would take the whole squeeze and a long name would push the rank out instead of ellipsising itself. Both meters are INSIDE the capsule, which is the whole header, and that is not only composition: `ProgressBar`'s track is `bg-surface-1`, which IS the screen background, so a bar out on the header would have been a fill with nothing behind it — the same mistake the ring made against a raised `Panel`. Inside the `bg-surface-2` capsule the track reads as a well. **Neither meter follows the equipped cosmetic**, and that is the one place in the app where not following it is the deliberate answer rather than an oversight: they stack, so a per-cosmetic rank bar over a fixed-gold XP bar was one bar on every theme whose accent was also gold — see §7. The XP meter reached that column by way of its own bordered chip beside the capsule, which is worth recording because that chip is what paid for the tier width: it carried an "XP" kicker and the daily-streak flame, and at 96px it left "Grandmaster" and "Cyber Overlord" truncating for everyone who held them. The kicker went (`--color-xp` is reserved by the token contract for level and XP alone and the `LV` chip is the same colour, so `t('xp')` survives as the accessible name, carrying the PERCENTAGE with it — the capsule is a `<button>` and ARIA makes a button's descendants presentational, so both meters' `progressbar` role and `aria-valuenow` are dropped from the tree and a bare "XP" announced a bar with no progress in it. A descendant's LABEL still folds into the button's own name, which is the channel that survives, and a browser that does not flatten still gets a real progressbar. That is also why the placement meter reads out and this one did not: its label was already "Placement 2/5" and carried its own number), then the chip itself went, and the **daily-streak flame left the menu altogether** — it is still in `ProfileModal` and `PublicProfileModal`, and the rally counters stayed where they already were rather than moving up here to replace it. `PROFILE` left the tab bar for the header pill alone and `SETTINGS` took its slot — PROFILE had two doors to one modal and SETTINGS had none in the bar at all. **Settings is the only one of the five that kept a modal**, because the in-match HUD opens it and a live court has no pager to put a page on; Ranks, Trophies and History each had exactly one entry point, so retiring their sheets left no second door to hold open. Retiring them dropped two things silently and both are back: History's refresh control — the list refetches on a `reloadKey` it does not own, so the sheet's button was the only thing that could ask the server again, and `e2e-history` caught it by timing out on a control that had stopped existing — and its three summary tiles, which read the page ON SCREEN through `onPageData` rather than a fixed "last 10" the tabs would quietly stop being true for. Nothing tested the tiles, so deleting them was silent; what found them was `tests/i18n.test.ts` reporting `history_record` and `history_peak_rally` as keys the product had stopped quoting, which is the dead-weight check doing a job it was not written for. **Account deletion moved with Settings, into the Profile modal**, last in its Stats tab, and the `screen === 'menu'` gate is MORE load-bearing there than it was in Settings: `ProfileModal` has TWO doors — the header pill and the in-match HUD's `#btn-open-profile`, one instance behind both — where `SettingsModal` only ever had one. Deleting from a live court would walk the player out of a match, and out of a DUEL, leaving an opponent alone in a room nobody was told about and charging the abandon to an account that no longer exists. Daily tasks folded onto the PLAY page as a grid of **all four dealt**, three regular and one elite, replacing a `scroll-x` rail of at most three UNCLAIMED ones — which could push the elite task, the permanent-unlock track, off the end of a sideways scroll, and which shortened through the day as tasks were claimed. It was also the last `pan-x` region nested inside the pager, so the gesture got simpler rather than more special-cased.

**Sheets stack explicitly now, and depth is a number rather than document order.** `Sheet`'s `LAYER` was three Tailwind class strings and Tailwind cannot generate a runtime z-index, so it is numeric bands instead — `default` 50, `over` 60, `gate` 70, plus the sheet's own index in the stack, capped at four so the top of the `gate` band lands at 74 and stays under `ToastHost` at 75 (convention §14) — a sixth stacked sheet means re-spacing the bands, not raising the cap, or two of them share a z and hand the decision back to the document order this exists to replace. A covered sheet is pushed BACK rather than offset: it scales down and dims in place, because a cascade drawn as an offset runs off the side of a phone. Only the top sheet paints a backdrop (two stacked blurs read as mud rather than as depth), a covered sheet is `inert` and its backdrop no longer dismisses it, and closing the top animates the one beneath back to rest — **that animation is the reveal**, with no extra machinery. App derives the stack with a `useMemo` over the booleans it already holds rather than pushing and popping, because there is no React context anywhere in `src/` and `isMultiplayerOpen` is driven by the relay handlers this section already records as load-bearing. It ends a live undefined behaviour on the way: `isSettingsOpen` and `isProfileOpen` were independent, both openable from the HUD, both at `z-50`, and two open at once resolved by which was written later in `App.tsx` rather than by which the player opened last.

**Player identity**: profiles are minted lazily from the device cookie in an *uninitialized* state and a blocking **OnboardingModal** gates everything — including taking a seat in a duel, refused by the relay itself, since a seat's display name is stamped at join time and never revisited — until the player locks in a **unique username** (case-insensitive, 3–16 chars `[A-Za-z0-9][A-Za-z0-9_-]*`, `Paddle-` prefix reserved for placeholders; rules shared client/server via `src/profileRules.ts`). The username then can't change for **365 days** from initialization (and from each later change); a released name returns to the pool. Optional **avatars** are exactly 256×256 PNGs — the client center-crops/resizes any image (`src/media/avatar.ts`), the server validates dimensions dependency-free (`server/image.ts`). Tapping any username (leaderboard, match history, lobby, in-match opponent) opens the sanitized **PublicProfileModal** backed by `GET /api/profile/:id`. Uninitialized profiles can't record matches and never appear on the leaderboard.

## 2. Tech Stack

- **Frontend**: React 19 (**with `@types/react`** — without it `tsc` silently skips every `.tsx`, so component props go entirely unchecked; that is how a DOM event came to occupy a `GameMode` parameter and a canvas read `theme.accent` on a type whose field is `accentColor`), TypeScript, Vite 6, Tailwind CSS 4 (CSS-first — configured in `src/index.css`, no `tailwind.config.js`), Motion (`motion/react`), Lucide React icons, Canvas Confetti.
- **Server**: Express 4 (`server.ts`) + **`ws`** for the WebSocket relay (no Socket.IO), Node 22. One process serves the client and the relay on one port, dev (Vite middleware) and prod (static `dist/`) alike. Runtime dependencies are only `express` + `ws`; everything else is dev tooling.
- **P2P mode**: private matches connect the two phones directly over **WebRTC DataChannels** (`src/net/p2p.ts`), with the relay as automatic fallback — see §5.
- **Audio**: procedural Web Audio API synthesis in `src/audio/soundEffects.ts` — zero audio assets.
- **Persistence**: **SQLite** via Node's built-in `node:sqlite` (no native deps) at `DATA_DIR/phong.db` (default `./data`), WAL mode with `synchronous = NORMAL` and a per-connection prepared-statement cache, managed by `server/db.ts` — recording a match compiles no SQL and fsyncs no log, which took the write from 0.93ms to 0.34ms. Avatars live in a separate `avatars` BLOB table (kept out of `SELECT *` hot paths); `recorded_matches` is the per-`(playerId, matchKey)` idempotency ledger that lets a match be reported by several paths and paid once (pruned after 14 days, indexed on `recordedAt` so expiry stays a seek and not a scan of the hot write path). `matches` carries a nullable `ranked` column — `ranksThisMatch` persisted at record time so history can filter Ranked from Un-Ranked; rows predating the column were classified once by the `ranked_backfill_v1` one-shot from mode + difficulty (rules assumed stock — shipping the column with NO backfill made a live server's entire history render Un-Ranked), and a NULL still reads as un-ranked as the safety net — and is trimmed to the newest 500 rows **per player** inside `insertMatch` (the global 500-row cap it replaced let one busy server's players trim each other's histories). One-shot migrations are flagged in the `meta` table — `placement_sigma_v1`, `tasks_reset_v1`, `ranked_backfill_v1` and `chaos_relabel_v1` (non-destructive data fixes; see §7) and the destructive `wipe_v1`…`wipe_v4` (the machinery: every wipe re-stamps ALL keys, since a half-stamped sibling would re-fire on the next boot and the pair would wipe alternately forever); each wipes all player data including `auth_secret`, which retires every existing device cookie — the client detects the resulting `403 PROFILE_NOT_INITIALIZED`, re-syncs, re-opens onboarding, and keeps the unrecorded match queued; there is no legacy-JSON import. The curated bot roster (`server/bots.ts`) is seeded once per database at **server boot**, flagged `bot_roster_v1` — deliberately not a schema migration, since a roster is a deployment decision and not a shape the database needs to be correct, and keeping it out of the constructor is what lets tests build a `db` with no bots in it. Seeding is per-bot fault-tolerant: a roster name a human already holds violates the unique username index, and that is skipped and logged rather than allowed to take the boot down. `npm run db:reset -- --yes` is the manual full reset (server stopped first). `node /app/dist/admin.cjs whois <username>` is the read-only support CLI (`server/admin.ts`, bundled beside the server) — it surfaces an account's **recovery code**, which is the only thing that reunites a player with an account their browser can no longer reach; it opens the file `readOnly` and deliberately does not import `db.ts`, whose constructor would run migrations and seed bots as a side effect of answering a support question.

## 3. Normalized Coordinate & Physics Model

All positions, velocities, and dimensions are normalized to `[0.0, 1.0]`.

```
                Opponent Court (remote / radar)
+-----------------------------------------------+  (opponent baseline y = 1.0)
|              [Opponent Paddle]                |
|                                               |
+===================== NET =====================+  (y = 0.0 for both players)
|                                               |
|                   (Ball)                      |
|                                               |
|               [Player Paddle]                 |
+-----------------------------------------------+  (player baseline y = 1.0)
```

### Cross-net transform (`server/transform.ts`, applied server-side)

When a client reports `ball_cross_net`, the server computes the opponent's view in one place so the two clients can never disagree:

- `x' = clamp(1 - x, 0.02, 0.98)` (horizontal mirror for head-to-head orientation)
- `vx' = -vx`
- `vy' = |vy|` (downward, into the opponent's half)
- `spin' = -spin` (mirrored court flips spin direction)
- `speedMultiplier` preserved

### Paddle deflection (`src/game/physics.ts`)

- Hit offset: `(ball.x - paddle.x) / (paddleWidth / 2)`, clamped to `[-1.1, 1.1]` (small edge forgiveness).
- Rebound angle: `offset × 62°` max.
- Each paddle hit speeds the ball up 4%, capped at `MAX_BALL_SPEED` (2.4 units/s).
- **Paddle drive & spin** (`driveCoupling`): the paddle's own velocity is an input, not just its position. Contact point decides how much of that motion *couples* into the ball — head-on is a clean rebound carrying `HEAD_ON_COUPLING` (0.22), an edge carries nearly all of it — and paddle speed decides the magnitude. The coupling feeds three things at once: rebound angle (+`DRIVE_ANGLE_DEG`), pace (+`DRIVE_SPEED_GAIN`), and **spin**. A stationary paddle behaves exactly as it did before, so nothing was taken away.
- **Spin never bends the flight.** Between impacts the ball travels perfectly straight; spin is carried on the ball and *spends itself on surfaces*, changing **both the angle and the speed** the ball leaves every surface with — `SPIN_WALL_TILT_DEG` / `SPIN_REBOUND_DEG` for the angle, `SPIN_WALL_SPEED_GAIN` / `SPIN_PADDLE_SPEED_GAIN` for the pace, with spin reversed and damped each time (`SPIN_WALL_RETENTION`, `SPIN_PADDLE_CARRY`). The pace trade is signed by `spinPace()`: a ball spinning **with** the direction it leaves in skids on, one spinning **against** itself is scrubbed — so spin buys angle at a cost in pace, or the reverse, instead of being free. Mirroring the court flips both spin and `vx`, so the product is identical on either half and the two phones can never disagree about how fast the ball now is; every rebound is held inside the match's own speed band, so a ball cannot be spun faster and faster off alternating walls. A curving-in-flight model was built first and rejected: it makes the ball's path unreadable on a blind half-court, where the receiver never sees the stroke that caused it.
- **`predictLanding(ball, spinFactor)`** is the single source of truth for where a ball will cross the paddle line, folding wall rebounds under the same rules the ball obeys. `spinFactor` 1 is the true landing; lower values are what an AI that reads less of the spin expects instead.
- Until this was built, spin was **documented but fictional**: `BallState.spin` existed, `ball_cross_net` carried it, `server/transform.ts` mirrored it, and the client hardcoded `spin: 0`. `checkPaddleCollision` likewise took a `paddleVx` argument it never read.
- **Paddle width (`PADDLE_WIDTH_RATIO` = 0.22), ball radius and ball speed are the *stock* game**, adjustable per match via `src/matchRules.ts`. Fairness is kept by a **ranked band** around stock on every physics rule rather than by an all-or-nothing stock check: inside the band a tuned match rates normally (the ladder absorbs a 15% wider paddle the way it absorbs a better phone); past it the match still pays XP but moves no MMR, no rank and no tier. Bands are ±15% on paddle and ball size and on serve power, ±20% on serve angle, ±10% on the minimum speed and +20% on the maximum. `isRankedRules()` is re-derived server-side in `recordMatch` from the rules themselves; a client-set `ranked` flag is ignored. Telemetry, quick chat and auto-serve never affect ranking; the **opponent sonar does** (see §1) and is the only non-physics rule that does. **Rules are only half of what makes a match rated**, and the pre-match sheet used to ask only that half — it promised "counts for rank" for a Rookie solo match `recordMatch` was always going to refuse to rate (a solo result rates only at an EARNED difficulty), and for Practice and Split Screen, which record no rating at all. `unrankedReasons({rules, mode, difficulty})` is the whole verdict in one place, ordered most-fundamental-first — mode, then difficulty, then sonar, then the physics keys — so the sheet, the lobby and anything added later cannot each answer it differently. It is a DISPLAY predicate: the server still derives its own half from `isRankedRules` plus `soloCountsForRank` and never trusts it.
- **The first pointer is the paddle. The second one, while you serve, is the joystick.** A role is the pointer's **age rank** among the fingers currently down: the oldest drives the paddle — always, serving or not, locked to its centre with no grab offset — and the second, during your own serve, is the aim stick. Anything after that is ignored. That is the way the game is actually held: a player comes into a serve already holding the paddle from the point they just lost, so the held thumb keeps the paddle and the thumb they reach in with does the aiming. It used to be the exact reverse — the first finger down took the joystick and any later one drove the paddle — which conscripted the thumb they were already playing with and handed steering to the newcomer. Every other case falls out of the same rule with nothing extra to remember: all fingers up and the next one down is rank 0 and takes the paddle; the paddle thumb lifting mid-aim makes the aiming thumb rank 0, so it takes the paddle and the aim is dropped rather than the paddle being left with nobody driving it; and a serve that fires without the stick being released (the auto-serve timer, the space bar) simply ends the joystick role, leaving that finger at rank 1 so the paddle does **not** teleport to it at the instant the rally starts. That last case used to need its own `'spent'` bookkeeping. A consequence worth stating: **one finger can no longer serve**. A lone pointer is the paddle, so a serve takes a second finger — a tap of one inside `AIM_DEADZONE` is the plain default serve — or the space bar, or `autoServeSeconds`. `CourtCanvas` tracks the ranking the way `SplitScreenMatch` tells two players' thumbs apart. A pointer the system CANCELS never serves, only a lifted one does; they shared a handler before, so a notification shade or an edge-swipe fired the serve.
- **The aim is a true joystick, and a pull is a slingshot.** The DIRECTION of the drag is the direction the ball leaves in and its LENGTH is the power (`aimFromPush` → `serveVelocity`, bounded by `serveAngleMax`/`servePowerMax` and the match speed band). Push and the ball goes where you pushed; **pull and it is inverted through the anchor**, so the ball still goes where you aimed — which is what gives a player at the bottom of the screen the whole court above them to pull away from, instead of the ~10% below the paddle a push-only gesture left them. Both reach full power equally; neither is the privileged gesture. What this replaced decomposed the drag into independent axes — sideways for angle, upward for power — and clamped power at zero, so a pull did nothing at all. `AIM_FULL_PUSH`/`AIM_DEADZONE` are fractions of the canvas **width on BOTH axes**, deliberately: they used to be width horizontally and height vertically, which makes a circle in those units an ellipse on a tall phone, so the direction pushed and the direction served were simply different angles. The angle is measured against **this match's** limit (`SERVE_MAX_ANGLE_DEG * serveAngleMax`, passed in) rather than the stock 55°, or the aim would compress or stretch the moment the rule was not 1. The mapping lives in `src/game/physics.ts` rather than in the canvas component, so it is a rule the fast test layer can state instead of something only a browser can observe.
- **One overlay, and one line.** The joystick **floats** — it anchors wherever the aiming thumb lands, so either hand works and nothing has to be aimed for before it exists — and draws a semi-transparent **upper half-disc** that fills from its centre to its circumference with power. Always the upward half, whichever way the thumb is dragging: it shows the RESOLVED serve, which is what makes a slingshot legible rather than surprising. Beside it, a **single line from the paddle** along the exact path the ball will take, its length the power. There were TWO overlays — a ring, deadzone circle, knob and its own line at the anchor, AND a separate dashed arrow from the paddle with an arrowhead and a power bar pinned to the bottom of the screen — two competing pictures of one gesture. **The ball is held on the paddle while all this happens**: locked to its top centre (`SERVE_BALL_Y`), tracking it, and launched from exactly that point, so the ball being aimed is the ball that leaves. Nothing was drawn there before — the court had no ball on it while a player lined a serve up, and a match opened with a stray active ball at mid-court that only the serve-gated physics loop kept from being loose. The whole thing vanishes the instant `isServing` goes false. `autoServeSeconds` fires a held serve by itself so a PvP match can't stall — and a **ranked duel must carry one**: `normalizeRoomConfig` forces 5s when the rules sit inside the ranked bands and the timer was off, since with rating on the line "off" would let a losing player stall forever. Every duel (re)start also runs a **3-second countdown per phone**, armed by `game_start` but started only when that player actually reaches the court (behind the lobby it would burn away unseen); no serve, aimed or automatic, fires under it.
- **The AI serves like it plays**: `aiServeDelay()` waits 0.6–1.15s scaled by competence and by `playerPressure()` (score gap + best rally this match), and `aiServeAim()` plays away from where the player is standing, committing harder and hitting harder as competence rises — with a coin flip when the player is dead centre and has left neither side open, since a bare `> 0.5` resolved that tie the same way every time and made the first AI serve of every match predictable. Both replaced a flat 900ms timer with a random angle. The AI serves out of the middle of its OWN paddle, the same rule the player's serve obeys; it used to launch from a hardcoded centre no matter where it was actually standing.

## 5. Real-Time Protocol (`server.ts`, path `/ws`)

Plain JSON over `ws`. Message shapes are the source of truth in `src/types.ts` (`WSClientMessage`, `WSServerMessage`) — update those first when changing the protocol.

**Client → Server**

| `match_sync` | `matchSeq`, `p1Score`, `p2Score`, `bestStreaks`, `streaks`, `earnedBests`, `servingPlayer`, `crossingsThisPoint` | A **P2P** match's own account of itself, so the relay still knows the score (absolute, not a delta; the scores and the peaks applied as a maximum, never echoed back). All three streak fields are per SEAT — each player is rated and paid on their own run, never the other's. `streaks` is **assigned**, not maxed: it is the live run, which legitimately goes back to zero on a miss, and a maximum would save a broken run as though it were still going (bounded by the peak, since a run cannot stand higher than it ever reached). It also carries where the POINT is, because a P2P link can die mid-rally: `sendGame` starts returning false and crossings go back to the relay, which judges them with `countReturn` — and that asks "was this the serve?" from exactly `servingPlayer` and `crossingsThisPoint`. **Sent on every crossing**, not once per point: the relay resumes from what it was last told, so a sync per point left every return since crossing one missing from the streak, the XP and the daily tasks — and the phase wrong by the same amount, so the next relayed crossing was miscounted too. Each carries a `rev` that only rises, and the room refuses anything at or below what it has applied: both peers run the same replica over the same events in the same order, so the same number is the same moment and the second copy is a duplicate — which, arriving after a relay-counted crossing, would assign the streak and the point phase back to before it. That counter is the **peers'** clock and the relay never advances it with its own crossings. A revision cannot settle everything, though, because a fallback is **one-sided**: the peer that notices first relays a crossing, and the peer that has not noticed hears about it only as a `ball_incoming`, which its replica never sees — so its next snapshot is a genuinely LATER revision describing a match one return short, and the fields a snapshot ASSIGNS would undo what the relay counted. That is not an ordering problem but an authority one — and reconciling the two accounts after the fact only trades one wrong answer for another (discard the return the relay counted, or discard the point the still-open peer scored). So they are not reconciled: `takeOverFromP2P` broadcasts **`p2p_fallback`** on the first counted event and both phones come off the DataChannel, leaving the relay the only thing keeping score. `room.relayCounted` (set there, cleared by every match start) is the guard behind it, because a broadcast is a request and a client takes a moment to act on one: while it is set, the relay stops taking the fields a snapshot ASSIGNS **and its peaks** — a maximum looks safe because it cannot go down, which is exactly why a diverged replica reading a serve as a return makes that extra hit permanent. Only the SCORE is still taken, since it only rises and refusing it would leave a half-fallen-back match undecidable. Almost nothing is lost by it: a peer stops syncing the moment it falls back (`sendGame` returns false, so the replica never counts and never syncs), so a snapshot arriving after the flag is either the diverged peer's — which is the case being refused — or one that was already in flight when the split happened, carrying a real return the relay never counted. Those two are indistinguishable in the message, and refusing both is the deliberate side: an understated run is recoverable and self-corrects on the next match, while a peak taken from a diverged replica is a maximum, so it is permanent — in the career best, in XP already paid, in daily task progress, and in an elite task's theme unlock. The window is one network delay rather than the rest of the match, and the SCORE is taken either way, so the result is never in question. Sharing it looked right and was the reverse: a DataChannel does not fail for both peers at the same instant, so the peer that noticed first relayed a crossing while the peer that had not sent its next revision — the one the relay had just taken — and that legitimate snapshot, often the one carrying the final score, was refused as stale. **A snapshot claiming BOTH seats at the winning score is refused outright**, before the revision is bumped and before it can set `inPlay`: a replica stops at the first score to reach the cap, so no honest peer reports two winners, and the two scores are clamped INDEPENDENTLY — so one message of `[999, 999]` became `[cap, cap]`, reported the match decided, and left `recordRoomMatch`'s `mine > theirs` false for both seats. That filed a real ranked LOSS against each player, two red down-arrows and two loss rows, while each phone's own `score_update` — which tests its own side first — showed them both VICTORY. The whole snapshot goes rather than being repaired: a peer wrong about who won the match is not one whose streaks, peaks or serving seat are worth taking either |

**REST API** (same origin): `GET /api/health` (carries the `build`), `GET|POST /api/session` (heartbeat / take the account), `POST /api/session/reset` (a new device identity for a released device; the release row is KEPT, so an account left behind stays traceable), `POST /api/session/end` (takes `{sessionId}` — the page's OWN session; a handback naming one it no longer holds is a no-op, or a closing tab signs its sibling out), `GET /api/rtc-config` (STUN list + time-limited TURN creds when `TURN_URL`/`TURN_STATIC_SECRET` are set), `GET /api/rooms/:venueRoomId/tables` (the open tables in one PvP room, for the browser — filtered on the venue, on `visibility === 'public'` and on having a live player, that last so "empty tables are never listed" holds inside the 15s before the reaper sweeps; a room with `listable: false` is a 404 rather than an empty list, so the queue's room is excluded as DATA), `GET /api/room/:roomId` (adds `waitingMs` — how long it has had nobody to play against, or null while both seats are filled — plus `venueRoomId`/`visibility`/`spectatorCount`/`spectatorsEnabled`, added rather than redefining `playerCount`/`isFull`, which still mean PLAYERS), `GET|PUT|DELETE /api/profile/me` (the profile carries `ladderPosition` for the top rung only — computed against the leaderboard's own filters and order so the two cannot disagree, and gated on the row being one the board would list. That gate is correctness, not cost: the relay's own hot paths take `db.matchmakingRating` instead of a profile, because a queued Overlord is exactly the account the tier gate does NOT spare; PUT takes `{username}` and/or `{cosmetic}` — 409 `USERNAME_TAKEN` / 403 `USERNAME_LOCKED {unlockAt}` / 403 `COSMETIC_LOCKED`, the last re-derived server-side from the profile because the picker that hides a locked cosmetic is the client; **XP is never accepted from the client**. DELETE takes `{username}` too and erases the account — see below), `POST /api/profile/initialize` (one-shot onboarding username claim), `GET /api/username-check?u=`, `POST|DELETE /api/profile/me/avatar` (raw 256×256 PNG body, route-scoped 600kb limit), `GET /api/avatar/:playerId` (immutable-cached, `?v=avatarVersion` busts), `POST /api/profile/claim` (recovery-code transfer; accepts an `active` **or** `released` device — see below), `GET /api/profile/:id` (sanitized public profile — carries `ladderPosition` too, because a position is not a rating: it is the one rank number already public, so a stranger reads the same `#7` the player does — registered LAST so `me`/`claim` etc. match first, with only the two-segment `/api/profile/:id/matches` beside it), `POST /api/match/record` (403 for uninitialized profiles; idempotent per `matchKey` — a replay returns the first result with `alreadyRecorded`), `GET /api/leaderboard?sort=elo|level|rally|wins` (`sort` is matched against that allowlist and `limit` bounded to 1..100 — it was a bare cast and a `Math.min(100, parseInt(…))`, so `?sort=bogus` built `ORDER BY undefined` and 500'd with the SQL error text, and `?limit=abc` gave `NaN`, which the only cap — a JS loop guard — never satisfies, so it returned the ENTIRE board from an unauthenticated route. The `LIMIT` is in the SQL now rather than only in that loop, and four partial indexes cover the sorts: every eligible row used to be materialized as `p.*` and run through `rowToProfile`, which `JSON.parse`s the achievements column, before the loop discarded all but a page. At 10,000 players that was 78.86ms for `elo` and ~70ms for the others, synchronous, on the loop relaying `paddle_move` for every live match; it is 5.00ms and ~1.1ms now. The indexes are declared after the `addColumn` migrations rather than in `ensureBaseSchema`, because every one is PARTIAL on `initializedAt`, which does not exist yet at that point — declaring them there fails a fresh database outright, which `tests/db-wipe.test.ts` and `tests/shutoutRecount.test.ts` reported as fourteen silently *skipped* tests rather than a failure. Initialized profiles with progress on the sorted metric only — `elo` needs a ranked game, `level` XP, `rally`/`wins` a nonzero best; a row of zeros is not "last place", it is not on the board; bots are a curated roster and exempt from the progress filter, excluded unless `?bots=1` is asked for), `GET /api/achievements`, `POST /api/profile/me/streak` (`{mode, endStreak, endedAt, clientNow}` — where a run stands when no match is ending to say so, e.g. quitting an unfinished one; counts no match and pays nothing, and refuses `multiplayer`/`split` since the relay owns a duel's runs), `POST /api/practice/record` (`{bestStreak, earnedStreak, endStreak, endedAt, clientNow}` — server computes the XP, from the EARNED figure only, and holds a per-UTC-day cap), `GET /api/missions`, `POST /api/missions/claim` (`{missionId}` — 404 `MISSION_UNKNOWN`, 409 `MISSION_INCOMPLETE`/`MISSION_CLAIMED`), `GET /api/matches/me` (paged history: `?tab=all|pvp|solo|practice&ranked=all|ranked|unranked&page=N`, ten rows a page, response `{matches, total, page, pageSize}` — `matches` keeps its old name and shape so a stale bundle still reads it), `GET /api/profile/:id/matches` (the same rows and params, public — 404 unless the id resolves to a public profile, which also covers `me`; registered just before `/api/profile/:id`).

**Device identity** (`server/auth.ts`): the server issues each browser a signed HttpOnly cookie (`phong_device`) **on the document navigation**, before a line of client JS runs — HMAC-SHA256 over a random device id, secret auto-generated and persisted in the DB `meta` table. All profile/match/achievement routes resolve the player from the verified cookie; client-sent player ids are never trusted, and the WS relay resolves display names from the cookie's profile (clients no longer send `playerName` at all). One cookie jar = one profile, which is as close to "one profile per device" as the web allows.

**The navigation is what establishes it, and that is load-bearing.** `deviceIdentity` was mounted on `/api` alone, so the HTML document set no cookie and the booting client's first API calls minted it. Those calls are **concurrent** — the session mint and the heartbeat's first tick both fire on mount — and on anything slower than localhost several are in flight before any has come back, so each arrives cookieless and mints its **own** identity, appending its own `Set-Cookie`; the browser keeps whichever response landed last. Measured in a real browser at 250ms latency: **three device identities per page load**. Usually the last one wins everything and it merely litters `players`. But the window stays open for as long as the slowest of those requests, and a player who **onboards inside it** — which the invitation flow pushes them to do, since the link drops them straight on the modal — locks their username to the identity the cookie is about to stop being. The next profile read comes back uninitialized, onboarding re-opens, and the name they just chose is **taken, by themselves, seconds earlier**. That is "they got signed out and their account still exists but they lost access" with no transfer and no eviction anywhere near it — just a cookie race on a slow connection. A document GET always precedes the JS it delivers, so setting the cookie there means every `/api` call carries one and nothing mints a second; `index.html` is `no-cache`, so it is reached on every load. `readSession()` closes the client's half by waiting on any in-flight mint. Pinned by `tests/accountRecovery.test.ts` (the navigation sets exactly one, and a boot burst carrying it mints none) and `tests/sessionMint.test.ts` (the read never overlaps a mint). **Never add a middleware order in which an `/api` call can be the first thing a browser does.** Each profile carries a `recoveryCode`, which is a **sign-in credential the player keeps**, not a one-shot token — and **onboarding ends on it**: the account is made, and the last step shows the code before the player reaches the game. It is a step and not a toast because a code nobody read is a code nobody has, and the one moment a player is certain to be looking is the moment they made the account. It stays visible in the Profile modal afterwards, and only ever to the account's own device.

**An account belongs to every browser that has signed in to it** (`device_links`). Identity is the device cookie and cookie jars do not cross browsers — an invitation tapped in Messenger opens a webview that has never met this player, and **the web offers no device identifier to bridge that**: there is no serial, no advertising id, and fingerprinting would *collide* two identical handsets, which is worse than the bug it would fix. So the account remembers its browsers instead. `POST /api/profile/claim` **signs in** rather than transferring: the row still moves (`players.id` IS a device id) and the avatar and history move with it, but both browsers are recorded as members, the browser left behind is **not** tombstoned, and the code is **not** spent. A member that is not currently holding the account resolves as `superseded`, and `POST /api/session` brings the account back to it **with no code at all** — so simply opening Phong in a browser that has signed in before lands the player on their account, no wall and no prompt (the newest load wins, exactly as it already did for two tabs; a duel the displaced browser was in is not charged an abandon, since `seatStillHoldsAccount` fails for a seat the relay itself evicted) — the device cookie of a member is the credential; the code is what gets a browser *into* the set, not what it presents every time afterwards. `moveAccount` is the single path for both, so the code and no-code routes cannot drift. **It has to carry every table keyed on the id, or that table is orphaned by the rename** — so it walks `PLAYER_KEYED_TABLES`, the same list `deleteAccount` walks, plus `matches`, `device_links` and `released_devices` handled apart (their keys are not a bare `playerId`). It learned this rule twice: `player_mode_stats` was missed when it was added, so an account arrived on its new browser having played nothing, every carried streak back at zero, and the next match recorded there wrote that zero over the run the player actually had — and then the whole day-keyed family was missed the same way, which was worse than litter: orphaned `recorded_matches` stamps meant every match the account had already been paid for could be paid a SECOND time by a queued, retried or relay-vs-POST duplicate landing after a sign-in, `elite_completions` left behind silently took back permanent theme unlocks, and the daily tables reset mission progress, reroll spend, the abandon forgiveness and the practice XP cap. Each table clears the claiming device's own rows first: the primary keys would otherwise collide with the rows moving in, and orphans left by earlier builds make that reachable rather than theoretical. **One account, one live holder is untouched** — `seatStillHoldsAccount` had to learn about links to keep it (a linked-but-not-holding device's row no longer exists under its id, so `activeSessionId` finds nothing and "no owner" read as "not displaced"; without that line eviction silently stopped working). Because the code is reusable it is now worth guessing, so failed sign-ins are rate-limited per device and per IP, and `POST /api/profile/me/recovery-code` rotates a leaked one without costing the account. Signing in over an *initialized* profile is refused (`BROWSER_HAS_ACCOUNT`) rather than deleting it. `released` survives for databases carrying rows from before this, and is no longer written.

**An account can be deleted, and deletion is the complete thing.** `DELETE /api/profile/me` sits at the bottom of the Settings sheet behind two steps: the player's **username, typed exactly** — case included, untrimmed, and checked server-side as well, since a step that lives only in a client is a step a stale bundle or a mis-wired request walks past — and then a **reminder that it is permanent, which is itself the final confirmation**: two buttons, `DELETE` and `BACK`, and nothing else. `BACK` returns to the open Settings panel with nothing spent, and closing the sheet abandons the flow rather than banking it, so a half-armed confirmation is never waiting the next time Settings opens. The section is offered from the **menu only** and only for an initialized profile — from a live court it would walk the player out of a match, and out of a *duel*, leaving an opponent alone in a room nobody told and an abandon charged to an account that no longer exists. `db.deleteAccount` is the same rule `moveAccount` obeys with nowhere for a missed row to go: it walks `PLAYER_KEYED_TABLES` (every `playerId`-keyed table — the list is hand-written, so `tests/identity.test.ts` reads the live schema and fails when a table is added without being added to it), drops the `players` row, and clears `device_links` and `released_devices` **in both directions and for every browser the account belonged to**. That last part is the one that bites rather than merely litters: a surviving `device_links` row reads as "linked but not holding" in `resolveSession`, which is `superseded` — a full-screen wall telling another of the player's browsers that the account is live elsewhere, about an account that is live nowhere. `wipe_v1` shipped without dropping that table and learned it the same way. **`matches` is handled apart**, because those rows are not all one player's: every seat files its OWN row (`recordMatch` writes the reporter as `player1`), so a duel produces two and the second is the opponent's record of a game they played — deleting it would take that game out of their history while their career counters, which are not derived from that table, went on counting it. History READS are `player1Id`-only for the same reason: each seat's own filed row is the complete, correctly-oriented record of that match, and `getMatchHistory` matching the `player2Id` column as well is exactly how every duel used to render twice — two WIN cards for the winner, two LOSS cards for the loser. Their rows stay and only the pointers are scrubbed, id and name both (`DELETED_PLAYER_ID` / `DELETED_PLAYER_NAME` in `src/profileRules.ts`; the id matches neither `dev_` nor `bot-`, so `isLinkableId` already refuses to make it tappable, and Match History swaps in a localized label). The name is scrubbed because the username goes **straight back into the pool** — that falls out of the row going, since the unique index covers initialized rows only — and would otherwise sit in somebody's history naming whoever claims it next. The account's live relay sockets are closed explicitly (`closeAccountSockets`): neither existing eviction path covers a delete, because `seatStillHoldsAccount` asks whether anything has *displaced* this seat and after a delete nothing has — the row is simply gone, so "no owner" reads as "not displaced". The device cookie is **untouched**: this is still the same browser, it simply has no account, so the next profile read mints a fresh uninitialized one and onboarding opens — exactly the state a new phone is in, which is what deletion has to mean if the browser is to be usable at all. The client clears the on-device match queue before reloading, for the reason `startFreshIdentity` does: `phong_pending_matches` is a flat, unnamespaced key with no idea which account was active when an entry was parked, and the next flush would credit a deleted account's match to the fresh profile this browser is about to be given.

**One account, one live device** (`server/auth.ts`, `src/net/session.ts`). The device cookie answers *who is this browser*; it cannot answer *is this browser still the one holding the account*, and that gap was exploitable. A transfer **renames the player row's id** to the claiming device's, so the previous device's cookie stopped matching any row — and `getProfile` mints a fresh, uninitialized profile for any id it has not seen. A device that had just handed its account away was therefore indistinguishable from a browser the server had never met: it was quietly issued a new empty profile, allowed to **play a whole match on it**, and only told at the final whistle, when the finished match was refused and onboarding re-opened as if it were a guest. Two devices, one account, two concurrent matches. Three things close it:

- **A session cookie** (`phong_session`, HMAC-signed, 12h) minted per load by `POST /api/session`. The profile records the one `activeSessionId` that owns it; the newest load wins, since the player is sitting at the device they just opened. Displacing a session also **closes any relay socket it still holds** (`closeDisplacedSockets`), so a phone cannot keep scoring for the seconds until its next heartbeat — the upgrade check is only a snapshot, and since the relay writes a finished duel onto both seats itself, `recordRoomMatch` re-checks that each seat still holds its account (`seatStillHoldsAccount`) rather than trusting the seat it was handed. Every write (`match/record`, `practice/record`, `missions/claim|reroll`, `profile/initialize|me|claim`, avatar) sits behind `requireActiveSession`, and profile **reads** behind `blockReleasedDevice` so a retired device can never reach the lazy mint. The WS upgrade enforces the same rule — barred from recording a solo match, an evicted device could otherwise still play a duel, which the relay records itself.
- **Release tombstones** (`released_devices`): a claim records the device it took the account *from*, so the server can tell "a player whose account is alive elsewhere" from "a browser I have never met" and say so. `POST /api/session/reset` gives a released device a **new** device identity and an empty profile, never the account back, and it **refuses any device that still holds its account**, since for one of those a reset would swap the cookie while the initialized profile stayed behind under the old id: not deleted, merely unreachable. It is no longer the *only* way off a released device, and it no longer deletes the tombstone on the way out — see the next bullet.
- **A released device is not a dead end, and starting over is not a default.** This is the state a player reaches by following an **invitation link into a browser that is not the one holding their account** — a chat app's in-app browser, whatever a QR scan hands off to — restoring there, and then going back. The wall used to offer exactly one button, "start as a new player", which mints a new device identity and leaves the account behind reachable by **nobody, ever**: its row survives and its username can never be claimed again. A full-screen wall with a single button is an instruction, not a choice, and the reset then deleted the release row, so the account was not merely unreachable but untraceable — "my account still exists but I lost access" had no answer. Three things changed. `POST /api/profile/claim` accepts a **released** device (`requireRestorableSession`) and issues it a session on success, so the account's own recovery code brings it home in one move; this grants nothing new, since that device could already reach the same call by starting fresh first and restoring from the new identity — it just lost its device id and its release record on the way. `SessionGuard` leads the `released` wall with that restore box and puts "start as a new player" behind an explicit confirmation that says what it costs. And `session/reset` keeps the tombstone. `superseded` is deliberately untouched: it already has a non-destructive way out ("play here instead"), so it keeps the ordinary `requireActiveSession` gate. `released_devices` rows are no longer written by anything — the state now survives only for a database carrying rows from before `device_links`, so a fresh install never produces one (pinned by `tests/deviceRelease.test.ts`, which fails if a writer is ever added back) — but the client path stays live for exactly that: `startFreshIdentity` swaps in the fresh, empty profile **without a reload** (a recovery-code restore does reload, so it does not need this), so `carryRef` — the per-mode streak a page remembers for itself, preferred over the profile's own value on the reasoning that this page's own eyes win — has to be cleared explicitly, or the fresh account's first Solo or Practice session opens on the run the player just gave up, and `bestStreak` opening on it is what the career best, the mode best and rally achievements are keyed on. **A second piece of per-browser state needs the same clearing, for the same reason**: the on-device match queue (`src/net/matchRecord.ts`, `phong_pending_matches`) that a failed `/api/match/record` parks for later replay is a flat, unnamespaced localStorage key — it has no idea which account was active when an entry was queued. Left alone, a match that failed to record under the OLD identity is still sitting there the moment the fresh one finishes onboarding, and the next flush (keyed on `profile?.id`, which fires on every fresh mount including the reload a player takes after onboarding) credits it there instead — XP, rating, achievements and streaks earned by an account this browser no longer holds, paid to one that never played it. `startFreshIdentity` calls `clearPendingMatches()` alongside the `carryRef` reset, on the same reasoning `attempt()` already applies to an `evicted` result (dropped rather than queued, because replaying it would credit whatever identity comes next) — applied one step earlier, to a result that was queued before the identity moved on rather than discovered stale after. Deliberately **not** applied to a recovery-code restore: that path can legitimately sign the SAME browser back into the SAME account it already held (a `superseded` device coming back with no code, or a `released` one restoring with its own), and clearing there would discard a match that account genuinely earned and could still be paid — a narrower fix than "any identity change," left for whenever that path needs one. **A third piece of per-browser state needs the same call, and it is the cheap one** — which is why it belongs on this list rather than beside it: the meter origins (`src/components/ui/meterMemory.ts`) are module scope for the same reason the other two are per-browser, remembering where each progress bar last stood so a player walking back out of a match sees the bar MOVE rather than fill from empty. Nothing is paid or rated on them, so the entire cost is a meter animating from the wrong place — but a fresh account is level 1 and unplaced, which is the ORDINARY case and not an exotic one, so it inherits `menu-xp:1` and `rank:placement` from the account just given up and watches its placement meter slide DOWN from the previous player's 4/5 on the first paint. `resetMeterMemory()` goes beside the other two; `handleDeleteAccount` needs none of the three, because that path reloads the page and takes every module-scope store with it. **The replay loop must write back against the queue as it stands at write time, not the snapshot it opened with**: it awaits the network between items, `postMatchRecord` appends during those gaps (the same bad connection fills the queue and fails the match just played, so the pairing is ordinary rather than exotic), and replacing the whole queue with the snapshot's leftovers silently deleted that new match — against the one promise the file makes. It tracks what it actually *finished* with instead, and subtracts that from a fresh read.
- **A heartbeat** (`GET /api/session`, every 15s and on refocus). An eviction lands in seconds instead of at the end of a match. `SessionGuard` is a wall, not a toast: in these states nothing is recorded, so a dismissible banner would be the bug again. It walls off `released`, `superseded` and `stale_build` and **nothing else**. `offline` is not on the list — a dropped heartbeat is a cell handover, not an eviction. Neither are `connecting`/`none`, which do not mean "you may not play" but "we have not asked yet": blocking on those put a network round trip in front of the first paint, delaying the menu and the onboarding modal for every player on every load, and nothing is gained by it — writes are gated server-side regardless, and a match recorded before the session lands is answered `SESSION_REQUIRED`, which `postMatchRecord` resolves by minting one and retrying. A match refused as `DEVICE_RELEASED`/`SESSION_SUPERSEDED` is **dropped, not queued**: replaying it later would credit whatever fresh identity this browser ends up with for a match another account played.

**The unit of ownership is the DEVICE, not the tab.** `phong_session` is an *origin* cookie, so two tabs on one phone share it: the newest load overwrites it and both then present the same value, which the server sees as one caller. Cross-device — the reported exploit — is closed by that cookie being per-jar. Same-device tabs are reconciled client-side instead: `POST /api/session` returns the session id, the page keeps it **in memory** where a second tab cannot reach it, and `GET /api/session` reports which session actually holds the account, so a displaced tab concludes it for itself and raises the wall. That is a correctness aid for honest clients, not a boundary — a modified client can decline to check, and nothing is granted on the strength of it. Making it one would mean a per-load credential attached explicitly to every request and to the WS handshake, a wider change than this; it is the obvious next step if tab-farming ever matters.

**Every deployment force-refreshes session auth, by construction** (`server/build.ts`). A session token carries the `buildId` it was minted under and is signed over it, so a session from a build that is not the one being served resolves to `stale_build`; the client reloads onto the current deployment (guarded by `sessionStorage` so it cannot loop) and re-mints. **`SESSION_STALE_BUILD` must never be handled as "mint one and retry"** — that is what `SESSION_REQUIRED` is for. Minting under the new build without reloading is exactly how an old bundle survives a deploy: the retry succeeds, the next heartbeat says `active`, and the guarantee quietly stops holding while that client talks a protocol nobody serves any more. A match caught by it is queued before the reload, so the refresh costs nobody the game they just finished. The device cookie is untouched by all of this — **sessions are disposable, the device→account binding is not** — so a forced refresh never costs anybody their account. The id is `BUILD_ID` from the environment, else a digest of the built artifacts — **both** `dist/index.html` and `dist/server.cjs`. Vite rewrites the hashed asset names into index.html on every client build, and the server bundle moves whenever server code does, so between them the digest changes exactly when what is being served changes, and **not** when the same build merely restarts (a crash-loop must not log the field out). The server bundle is in there deliberately: hashing the client alone left a **server-only** deploy — an auth fix, a protocol change, precisely what this exists for — producing the same id as the deploy before it, so nothing in the field refreshed. In dev, with nothing built to hash, it is a per-process value. `index.html` is served `Cache-Control: no-cache`, or a client told it was stale would reload straight back onto the build it was already running. **This is the standing rule for the project, and it holds for every future update without anyone remembering to bump anything.**

**Smartphones only** (`src/device.ts`, `MobileGatekeeper`). Phong is two phones laid top-to-top; a desktop cannot play it meaningfully and a tablet is the wrong shape. The gate that was here decided by **viewport size** and, whatever it decided, always rendered the game — a desktop just got it inside a drawn phone bezel. Narrowing a browser window walked straight through it, which is how the concurrent-account report above was produced. The verdict now comes from the platform the browser reports and the viewport is **not consulted at all**: iPhone/iPod and Android carrying the `Mobile` token (or `userAgentData.mobile`) play; iPad, Android tablets, and **iPadOS reporting itself as a Mac** (caught by `maxTouchPoints > 1` — no Mac has a touchscreen) are turned away alongside the desktops. A phone UA without touch points is a spoof and is refused. This is a product gate, not a security boundary — device emulation reports a phone and is believed; what must not be bypassable is playing two matches on one account, and that is the server-side session rule above. `?desktop=1` bypasses it under `import.meta.env.DEV` only, so the branch is not present in a production bundle.

**The QR code is generated in-repo** (`src/media/qr.ts`): byte mode, versions 1–10, all four ECC levels, no dependency and no network call. The old gate fetched a 200×200 bitmap from `api.qrserver.com`, handing every desktop visitor's URL (room codes included) to a third party and breaking on any network that could not reach it. It renders as a single SVG path, so it is exact at any size. `tests/qr.test.ts` pins it against matrices from an **independent** encoder; during development it was additionally checked by decoding 237 generated codes with a real scanner library.

**P2P mode** (`src/net/p2p.ts`): the host offers a WebRTC session when the guest joins (lobby toggle, default on); signaling rides `rtc_signal` over the relay. Gameplay starts relayed and hands over when the DataChannels open — "fast" (unordered, no retransmit) carries `paddle_move`, "game" (reliable ordered) carries everything else. Peers exchange the same client-message shapes and each side synthesizes the server-shaped equivalents locally, replicating the room rules (score, serve rotation, rematch votes) deterministically and reusing `server/transform.ts` for the net cross. If the link never opens or dies, play continues on the relay (the HUD badge shows `P2P` / `RELAY`). Adding a gameplay message means handling it in **both** `server.ts` and `src/net/p2p.ts`.

**Mid-match disconnects**: a socket dying with a live, undecided ball is an **abandon**, judged by the relay from room state it owns — a client can never report one. **Walking out of a duel is losing it**: `vacateSeat` calls `recordRoomMatch` with the leaver's seat named, *before* the seat empties so the room is still whole, and the match goes down as a real LOSS for the leaver and a real WIN for the survivor at the standing score — history rows, career counters and rating alike, on the same `matchKey` so a racing client POST is a no-op. What that replaced was a flat `rankMu` penalty and no match recorded anywhere, which is how a player could quit every duel they were losing and keep a **100% win rate with no tracked losses**, while their opponents' wins evaporated with them. `db.recordAbandon` is now the bookkeeping half only: the day-keyed count (`daily_abandons`), the career counter, and the verdict on today's forgiveness. The first abandon of a UTC day is forgiven, and **forgiveness spares the RATING, never the facts** — the leaver's copy of the match records un-ranked (`RecordMatchContext.forceUnranked`, server-side only), while the survivor's win rates on its own merits; every later one that day rates like any other loss, which is the real cost of leaving and needs no flat penalty beside it. XP is untouched either way — levels never regress. Only a LIVE match is one that can be abandoned: leaving a lobby, or a room whose match already ended, records nothing (and `persistDuelStreaks` still keeps both runs for those endings, since no match record carries them). The surviving player is bounced to the main menu with a notice that says the win was recorded, instead of being stranded on a dead court.

**Every socket carries an `error` listener, and the relay survives a bad frame.** None did, `wss` had none either, and there was no `process.on('uncaughtException')` anywhere — while `ws` raises receiver and socket faults as an `'error'` emit, and a Node `EventEmitter` `'error'` with no listener **throws**, from a raw-socket I/O callback outside the `try/catch` that wraps the message handler, so nothing could catch it. One invalid-UTF-8 text frame ended the process; so did an unmasked client frame, or `RSV1` set with no permessage-deflate negotiated. `/ws` accepts cookieless sockets, so this needed no account and no room. Demonstrated both ways against a production build: before, the frame arrives and the process exits 1 with a 1007 status while `/api/health` answers nothing; after, one warning line and health still 200. Rooms live in process memory, so what that exit dropped was every live duel, every queued player and every spectator at once, without taking the graceful `SIGTERM` path. `maxPayload` is set with it, at 64KB: `ws` defaults to **100 MiB** per frame and every frame is `JSON.parse`d synchronously, and `rtc_signal` relays its payload byte-for-byte with no length check, so one seated player could stall the loop and spike RSS at will. The largest legitimate message here is an SDP offer.

**A room outlives nobody.** A seat is vacated by a close event, so anything that empties a room without one leaves it in the map forever: a half-open socket, or — the reported case — a socket that takes a SECOND seat, since `create_room`/`join_room` only overwrote the socket's `currentRoomId` and the abandoned seat then belonged to a socket no close handler would ever trace back to it. Two things close that. Taking a seat now vacates whatever seat the socket already held (which correctly charges an abandon if it was a live duel) — but **only once the new seat is certain**: vacating before the destination was checked meant a mistyped code, an expired room or a full one cost the player the room they were already in, and mid-duel charged them an abandon for a match they had not left. A join to the room the socket already sits in is refused outright rather than treated as a move, since the vacate would empty and delete that very room and the seat would then be taken in an object no longer in the map, and `reapRooms` (pure, in `server/room.ts`) sweeps every 15 seconds for rooms **nobody is connected to** — every seat vacant or holding a socket that is already gone. That last part needs the relay to *know*, and `readyState` cannot tell it: a peer whose network vanishes without a close handshake leaves the socket reading OPEN until a write times out at the TCP layer, which is minutes — and meanwhile the seat looks live so the room is not empty, `vacateSeat` never ran so `soloSince` is null, and the survivor's own `paddle_move` keeps `lastActive` fresh, so all three branches miss it and they sit opposite a phantom. So liveness is **asked for**: a 30-second `ping`, and a socket that did not answer the previous probe is `terminate()`d (`partitionHeartbeats`, pure and unit-tested). A terminate fires the close handler, which is the only thing that vacates a seat, so nothing downstream changes — it just becomes true. It also keeps the old 30-minute idle clock, and adds a 30-minute TTL for a room with **nobody to play against** (`soloSince`, started when a room is opened and whenever a seat empties without emptying the room, stopped while both seats are filled): `lastActive` is refreshed by every `paddle_move`, so a host sitting alone on a court streams their own room's idle clock forward indefinitely and no clock keyed on activity can ever expire one. That flag started as a one-way `pairedAt` set when a second player arrived, on the grounds that a room which HAS been a duel is one a rematch can still happen in — true only while the other player is still there, so a guest who joined and left made the room permanently exempt from the very clock the leak needed. `GET /api/room/:roomId` reports it as `waitingMs`, beside `inPlay`. A reaped room's still-live sockets are closed, and **the client tears down on any close while it holds a seat** — a room deleted out from under a player used to leave them on a court whose every message the relay silently dropped. That teardown used to require an *opponent*, which missed precisely the case the unpaired TTL exists for: a host waiting alone was left in a lobby advertising a room code the relay no longer knew, so a friend typing it got "room not found" while the host still believed they were hosting. It keys on the room, not the opponent, and says two different things — mid-match the relay has recorded an abandon and told the opponent, so "removed from the match" is true; alone in a lobby there was never a match to be removed from.

**A relay room is a TABLE, and it sits in a venue.** `Room` carries `venueRoomId` (a PvP bracket from `src/venues.ts`, the hidden queue room, or the hidden `_default` room a table created without a venue lands in) and `visibility`. The venue is what decides whether the match moves the visible ladder (§7), so it is read from the ROOM at record time and never from a payload — and `DEFAULT_VENUE_ROOM` is `_default` rather than `casual` for exactly that reason: the name used to carry two unrelated jobs, and making the ungated bracket unranked would otherwise have taken the ladder from every invite-code duel and every older bundle along with it. Public tables are listed by `GET /api/rooms/:venueRoomId/tables`, which the lobby polls every 3 seconds while its browser is on screen — a read, deliberately not a WS message, since browsing would otherwise have to be handled in both `server.ts` and the P2P replica for no gain. **`visibility` is the entire boundary protecting invite-code tables**: that listing is unauthenticated, so a private table appearing in it would make every private room's 4-letter code harvestable, which is why `tests/tableBrowser.test.ts` asserts the absence directly and was checked by removing the filter and watching it go red. **A room offers ONE create control**, and the table it makes is OPEN — listed in the room's browser, joinable by anyone in the bracket, with nothing to share and nothing to copy. There were two buttons, "start a table" and "host a match", and from the player's seat they were the same button: one made a listed table, the other an unlisted one, and both landed on the identical screen — a room code, waiting for somebody. Listed-versus-unlisted is invisible to the person who just pressed it, so it was never a choice, only a fork. **What came back in its place is a LOCK, which is a term of the table rather than a second front door**: `Private` sits beside "let people watch", takes the table out of the listing, and mints a 4-character `joinKey`. Turning it on AGAIN mints a new one — the point of a re-keyable lock is that a key already given out stops working, so sharing one is a decision the host can take back, which is exactly what a URL could never be. **The key is the only way in**: a locked table is deliberately NOT joinable by its room id, since the id is how the relay indexes the table and still answers `GET /api/room/:id`, so an id that also opened the door would make the key decorative. `roomForCode` is the one resolver both `join_room` and `spectate_room` ask — a locked table is not WATCHABLE by its id either, or the key would be a door with a window beside it — and it falls through to the room id only for a table that is public or carries no key at all (a room from an older bundle). Keys are minted unique against room ids **and** other keys, because a code typed into the join box is resolved against both namespaces. What the host may hand out is the four characters and nothing else: Copy puts them on the clipboard and Share calls `navigator.share({ text: key })` with **no `url`**, because passing one is precisely what turns a share back into a link; the Share button is feature-detected, so a device without a share sheet gets no button rather than one that silently does nothing. `visibility` stays in the protocol and stays private by DEFAULT at the relay — which is what keeps an old bundle, the invite flow and the test harness byte-identical, and what `tests/tableBrowser.test.ts` still asserts at the socket. **One consequence for anything driving the lobby**: an open table shows no code at all, so a suite can no longer read one out of the DOM — the table's identity is `#lobby-table`'s `data-room-id`, which is an index rather than a door, which is what it is. **The relay enforces the bracket the menu draws**, asking the same `roomEntryVerdict` the room list asks: on `create_room` it judges the HOST, and on a `join_room` that resolves to a PUBLIC table it judges the joiner (the browser is polled, so a listed table can be tapped by somebody who then fails the gate). A join to a **private** table is never bracket-checked — an invitation is an invitation, and the lock above is what puts that case back within reach of a player: turning `Private` on takes the table out of the listing and hands its host a key, and somebody arriving on that key is not judged against the bracket. Two friends in different brackets can play anywhere on a key, and in `casual`, which gates nobody, without one. Watching is checked by neither: `spectate_room` asks no bracket at all, because a bracket gates who may PLAY and watching the top of the ladder costs nobody a match.

**Matchmaking is a queue, and the band is a promise with an expiry** (`server/matchmaking.ts`, pure like `server/room.ts` and unit-tested without a socket). The brief asked for two things a low-population server cannot both have — "never match unless the win chance is 40-60% for both" and "always find another player" — because `winProbability` is symmetric, so a lone queuer never matches however long the search runs. So the band is a **target held for the first ninety seconds**: 45-55 for the first 30s, the brief's own 40-60 to 90s, then sliding linearly to 20-80 by 180s and stopping. It slides rather than stepping, so nobody is paired against a wall of a player the instant a threshold passes, and it is judged on the **more-waited** of the two — judging on the newcomer's own tight band would let a fresh arrival veto the pairing the wait was widening toward. Among everyone inside the band the closest to a coin flip wins, and a tie goes to the better `rttMs`, which is a **hint and never a gate**: it is self-reported, and forging it buys nothing but a marginally better-connected opponent. Deliberately **no geolocation** — there is no IP handling anywhere in this repo and this is not the thing that should add it. On a pair the relay **seats and starts, with no lobby and no ready tap**: a table in the hidden `_queue` room, private, no watching seats, both sockets sent the ordinary `room_created`/`room_joined`/`room_config` so no client handler had to learn anything, then `startMatch` itself. **Why skipping the handshake is sound here and nowhere else**: the guest-ready step exists because a room's terms are the host's to change ("a yes to old rules is not a yes to new ones"), and a queue table has no host and no editable terms — `DEFAULT_ROOM_CONFIG` plus the ranked auto-serve floor, stated in the searching UI before anybody joins, and `set_room_config` refused outright on a `_queue` table so the premise holds by construction. **Queueing is the yes.** Consequences, deliberate: a no-show bleeds points to the 5s auto-serve and takes a real loss (both consented by queueing, and it is the stall rule ranked duels already carry); a socket that dies before the countdown ends is the ordinary case, since `inPlay` is false and no abandon is charged. `accept()` in `useQuickMatch` survives as a documented no-op and the `declined` status is unreachable — the union was the frozen contract and an unreachable arm costs nothing. A queue place and a seat are **one commitment**: taking either gives up the other, and a socket's close releases both. Re-joining keeps the original `joinedAt`, so nobody widens their own band by asking again. The queue is an in-process array beside the room map, swept every 2 seconds (and immediately on each join, so a newcomer never sits out a tick) — single-instance by design, exactly like the rooms.

**The room owns the match, not either phone** (`RoomMatchConfig` in `src/types.ts`). The winning score and every physics rule live on the room: the host sets them in the lobby while waiting, the server normalizes and broadcasts them, and `game_start` carries them again so no phone can begin a match on terms it was not told. **A duel starts by handshake**: the guest clicks Ready in the lobby (readiness clears whenever the host edits the terms — a yes to old rules is not a yes to new ones), only then does the host's Start button enable, and the server-broadcast `game_start` is what closes BOTH lobbies. Quitting a live duel asks for confirmation (an abandon is at stake); a player whose own socket dies is told they were ejected and returned to the menu, exactly like the survivor. Before this, each phone applied its own `settings.winningScore` and `settings.rules` — picked in the **Solo** panel, the only place the controls ever appeared — so a duel could be two different matches, and the shorter one ending first left the other player stuck mid-rally with a live court and no way forward. The server also tracks `inPlay` (a ball has crossed) and `matchOver` (the authoritative score reached the room's winning score): settings are editable only outside a live match, and a `rematch_request` is ignored unless the room agrees the match is finished, so a vote can never be banked mid-rally. `src/net/p2p.ts` replicates all three rules exactly.

**Every match is recorded, once, on every profile it belongs to.** A duel used to be recorded only by whichever phone POSTed it, so a result reached a profile only if that player's client survived the final point — a phone that locked, backgrounded, lost signal or was simply closed on the losing screen recorded nothing, and the match had happened for one player and not the other. The **relay** now writes a decided duel for **both** seats the moment the score decides it (`recordRoomMatch`), from the score it owns, and pushes each player their own `match_recorded`. The clients still POST — that is the fallback for a match the relay never saw — so the same match legitimately arrives up to three times, plus a retry and a replay from the on-device queue. What makes that safe is that **a match has an identity**: `matchSeq` (from the room, carried on `game_start`) plus the room code give `duelMatchKey()`, a solo match mints its own key, and `recordMatch` writes one `recorded_matches` row per `(playerId, matchKey)`. The first call is paid; every later one is answered with what it paid (`alreadyRecorded: true`) against a live profile and live missions. **Never add a match-recording path that has no `matchKey`.** And **never read a number off a match payload without coercing it**: `bound()` in `recordMatch` exists for exactly that and the two SCORES were the pair that never went through it, three lines below it, under a comment claiming "Everything else read off the payload is bounded; this is too." `playerScore` reaches `matchXp` and is multiplied by `XP_PER_POINT`, so `1e307` produced `Infinity`, and `levelFromXp`'s `while (xp >= next)` — over an `xpForLevel` that was itself O(level) — then never terminated at all: one authenticated POST wedged the single-threaded process for good. `1e9` was the quiet version, level 24,492 in 448ms of blocked event loop and permanent because XP never regresses; and `"5"` slipped past every eye because `matchXp` still computed numerically (`"5" * 12 === 60`) while `totalPointsScored += "5"` concatenated 100 into 1005, clearing `points_100` and `points_500` on the spot. Both ends are closed rather than one, because either alone leaves the other latent: the scores are bounded by the longest match anybody can play — a score above the largest winning score is not a big number, it is a lie — and `xpForLevel` is now the closed form `(L-1)(250 + 30(L-2))` with `levelFromXp` solving for the root instead of counting to it, so no input can loop whatever reaches it. And **every one of them rates a duel from the same pre-match pair** (`duelStartRatings`, cached on the room and keyed on `matchSeq`, so a rematch re-samples). Both paths used to read the opponent's rating live, so whichever committed first moved that player's rating and the other seat was rated against an opponent that had already played the match — worth about a full μ, always in the same direction. In a P2P duel the two paths travel different connections (the deciding `match_sync` over the WebSocket, the POST over HTTP), so which lands first is a race. The cache is populated **eagerly**, at every one of the three moments a room begins a new match (`startMatch()` — a host's `start_match` and a relay-mediated `rematch_request` both wrap it — and the P2P-agreed-rematch branch inside `applyMatchSync`), not lazily at whichever recording path touches the room first. Lazy population was argued safe on the grounds that every recording path samples strictly before it writes — true of this room's own two paths racing each other, and not the whole story: an unrelated write moving the same player's rating (a queued SOLO match replaying mid-duel, on the same page) between `game_start` and whichever path happened to touch the room first was already baked into the sample by the time it was taken. **A snapshot sets `room.inPlay` only on evidence that a ball has been in play** — a point on the board, or a crossing in the current point — while the P2P-agreed-rematch branch inside `applyMatchSync` clears `inPlay` for the new match. That function is the untrusted-peer boundary: a snapshot naming a match with a 0-0 score and no crossings describes a match that has not begun, and reading it as one in play would charge a player who leaves during the countdown an abandon — past the daily forgiveness, a ranked rating penalty for a match nobody played.

**The room's cross-check is bound to one match, and to one it has actually decided.** `/api/match/record` re-derives a PvP result from room state rather than trusting the client's numbers — but a room outlives every match in it and `startMatch` resets it to 0-0, so the cross-check applies only when `room.matchSeq` equals the match the payload names **and the room's own score is not level**. Unqualified, it overwrote a slow or replayed POST with the *next* match's blank score and filed it as a 0-0 loss. The same blind spot was far worse in **P2P**, where scoring never passes through the relay at all: every P2P duel was overwritten with 0-0 and **both** players filed a loss, which is why winning one never completed "win a match". `match_sync` closes that — it is also what restores abandon detection and the mid-match settings lock for P2P, both of which silently did nothing there. **The level-score half is a second, likelier route to the same two red arrows and needed no malformed message at all.** In a P2P duel the deciding `match_sync` travels the WebSocket while the client's own POST travels HTTP, so the winner's report legitimately arrives first, against a room still reading 0-0 — and the cross-check then set `playerScore` to 0 and `isWinner` to `mine > theirs`, which is FALSE, filing the WINNER a 0-0 loss. The shared `matchKey` deduped the relay's correct record away afterwards, so the wrong one stood. A room that has not decided the match has nothing to say about it, so the client's own account stands there.

**But "the client's own account stands" is about the SCORE, and it never meant the ladder.** Whether a room can *decide* a match and whether one can *vouch* for it are different questions, and only the second gates the rating. With no `roomId` at all the payload was unguarded three ways at once: the client's scores stood unexamined; `payload.matchKey` is only derived when a `roomId` is present, so the `recorded_matches` ledger was skipped entirely and the identical body could be replayed without limit; and `isRankedRules(undefined)` and `roomCountsForRank(undefined)` are both `true`, so it rated — against an even fallback opponent, since no opponent rating reached the context either. Thirty identical POSTs, about a second of wall clock, took `rankMu` from 25.000 to **47.177** and `rankedGames` from 0 to 30: Cyber Overlord, whose floor is 37, and with it the top-100 ladder position, `tier_overlord`, `legend-aurora`, `duel_10`/`duel_50` and `elite_duel_3`'s permanent theme. So a `multiplayer` payload that does not resolve to a live room seat the caller occupies is `forceUnranked` and given a device-scoped key: XP is still paid, which is the same trade every solo result already gets, and the ledger collapses the replay to the one match it was. **Vouching asks three things, and it took two goes to reach them.** `!room || seat < 0` was the first, and it closed the roomless payload while leaving the identical exploit one step away: **CREATE a room, sit in it alone, and POST**. The room exists and the seat is yours, so it vouched — and a fresh room mints a fresh `matchKey`, so the whole thing repeats without limit. Measured over 25 rooms with no opponent and no match ever started: `rankMu` 25.000 → **45.817**, tier overlord, 25 ranked games. So a live seat, an **opponent in the other one**, and a claimed `matchSeq` naming a match this room **actually started**. `matchSeq` is 0 on a fresh room and `startMatch` is its only writer, and `start_match` is refused until a guest has readied — so `seq >= 1` is precisely *two people agreed to play this*, which no lone socket can manufacture. Narrowness is still load-bearing in the other direction: gating on the room's *score* instead force-unranks the legitimate P2P race described in the paragraph above, which `tests/duelRecord.test.ts` catches on the first run under the name it already had, and that race passes all three of these — it is only the SCORE that is behind. Two honest costs, both taken deliberately because the failure modes are not symmetric: a duel whose room was reaped before a retried POST landed pays XP and no rank (the same absence-versus-safety call `RecordMatchContext.venueRoomId` documents, decided the same way), and so does a pure-P2P duel in which no deciding `match_sync` ever reached the relay AND the opponent's socket closed before the POST — a narrow window, since the replica syncs on *every* crossing, so the relay has almost always recorded that match itself.

**Trust model — deliberate trade-off**: gameplay physics is client-authoritative (each client simulates its own half and reports `ball_cross_net` / `point_scored`, or `match_sync` when the points are going over a DataChannel). This keeps the local half at zero latency and is fine for friendly play, but a modified client can cheat about the *match it is playing*. The server validates room membership, owns the shared score, caps chat length, coerces and bounds every field of the transformed ball, and holds a synced score inside the room's own winning score. Revisit only if public leaderboards attract abuse.

**The line that trade-off does NOT cross is a message that costs somebody else something.** "A modified client can cheat" has always meant its own result, and four handlers were quietly outside that: they let one socket spend another player's rating, another player's rally record, or the whole process. Each is closed, and the shape is worth keeping because a new gameplay message is likely to have it too.

**Every gameplay message is coerced, and `paddle_move` was the one that was not.** It forwarded `1 - msg.x` to the opponent and `msg.x` raw to the watcher, with no `Number()` and no clamp — while `ball_pos`, fifteen lines below it, does `Math.max(0, Math.min(1, Number(msg.x) || 0))`, and `quick_chat`, `swap_seat`, `spectate_room` and `match_sync` all validate. So `"abc"` became `NaN`, serialized as `null`, and landed as `1` on the opponent's court; `1e308` drew their chevron at `-1e308`; and an object was relayed to a spectator whole. `transformBallForOpponent` had the same gap on the far side of the same rally: it clamped `x` and let `vx`, `vy`, `spin` and `speedMultiplier` through on `Math.abs`, unary minus and `|| 1`, every one of which answers `NaN` for a non-numeric input. `{ vy: 'x' }` is the sharp one — on the receiving court `b.y += NaN * dt` makes every comparison after it false, so the ball never bounces, never crosses and never scores, `isServing` stays false so auto-serve never arms, and **the point never ends**. The victim's only way out is quitting, which is recorded as an abandon: a real ranked loss for the player who did nothing. Bounds there are sanity limits on a hostile payload rather than game rules — 8 per velocity component against a `MAX_BALL_SPEED` of 2.4 — so the rules-aware clamp stays on the receiving client where it belongs, and `vy` keeps a floor because a zero is the same freeze by another route.

**Nothing is counted after the final whistle.** `point_scored` and `ball_cross_net` both ran with no `matchOver` guard. The first incremented an unbounded score, so `decided` stayed true and every later message re-entered `recordRoomMatch` — about thirty synchronous SQLite queries each, on the loop that serves every other match. The second is the one that left a mark: `countReturn` kept bumping `room.bestStreaks`, `startMatchStreaks` opens the NEXT match's peak *on* `room.streaks`, and `recordRoomMatch` reports that peak as `bestStreak` — so winning a match, spamming crossings, then playing a rematch wrote a permanent `highestRally` and took `rally_150`, `perpetual-blue` and `quantum-gold` with it. Measured at the socket: 300 of each message past a real 3-0 duel relayed 300 `ball_incoming` and 300 further `score_update`s before, and nothing at all after.

**A `match_sync` is a REPLICA's account of a match, so it is refused from a table that never had one.** The handler asked only for a seat, and `applyMatchSync` takes the score as a maximum and will declare the match decided on it — while broadcasting no `score_update`, so the opponent's client renders none of it. On a purely relayed table one message naming the winning score for your own seat therefore filed a real ranked win for the sender and a real ranked loss for the other player: measured, `rankMu` 25.000 → 30.783 for the sender and 25.000 → 22.372 for the victim, plus a fabricated career-best rally of 50, from a single frame. `Room.p2pOffered` is set when BOTH seats have taken part in a handshake — an `offer` from one and an `answer` from the other — and survives a transport fallback, since a link that opens and dies leaves a peer that legitimately still holds its replica, which is the one-sided fallback `relayCounted` exists for. **It does not survive a SEAT change, and "set once and never cleared" was the second half of the same bug**: a room outlives its occupants, so evidence about the pair who negotiated it left the table permanently able to vouch for a replica — the guest leaves, a stranger takes the seat, and that newcomer forges a decisive snapshot against a victim who was never party to any DataChannel. `clearP2PEvidence` resets the offer, the answer and the flag together in `vacateSeat` and in `swap_seat`'s playing-seat branch; resetting only the flag would leave the next occupant holding one half and needing to supply just the other from their own single socket. **One seat's signal is not a handshake, and shipping it as one left the exploit reachable from a single socket**: the relay was a pure pass-through with no shape check at all, so `{}` was a signal and a signal armed the guard, meaning the attacker still needed nothing whatever from the victim. The relay stamps which seat each signal came from, so an offer and an answer from *different* seats is the one thing a lone socket cannot manufacture. `acceptRtcSignal` (`server/room.ts`, pure and unit-tested) is also where the payload is finally validated against the three real kinds and `sdp` bounded at 16KB — `quick_chat` capped at 100 characters and this capped at nothing — and **`ice` deliberately advances nothing**, because candidates trickle in any order, arrive from both seats, and a null one is the legitimate end-of-candidates marker, so counting them as evidence hands the one-frame arming straight back. It **narrows rather than closes**, and that is the honest claim: on a table where the victim's own client is genuinely negotiating P2P this becomes true legitimately and a modified peer can still lie in a snapshot, which is the client-authoritative trade this section already documents. What it removes is the case where the victim was never party to a DataChannel at all — a spectated table, a client with P2P off, a browser without WebRTC. **The guard is authority, not arithmetic, and the difference cost a first attempt**: step-limiting the score to +1 per revision looked cheaper and broke seven tests in `room.test.ts`, correctly, because a snapshot is absolute rather than a delta and is applied as a maximum *by design* — a P2P relay never sees the intervening points, so capping the advance leaves a legitimate match undecidable.

## 6. Audio Engine (`src/audio/soundEffects.ts`)

Entirely procedural Web Audio API:

- **Paddle impacts**: pitched oscillator bursts scaling with rally speed and hit offset.
- **Wall bounces & net crossing**: filtered sweeps and noise wooshes.
- **Chiptune BGM**: procedural arpeggiator, tempo scales with rally intensity.
- **Soundscapes**: `stadium` (crowd synthesis), `cyberpunk` (analog drone), `zen` (pentatonic chimes + wind), or `none`.

The `AudioContext` must be unlocked lazily from a user gesture — never play audio before `sound.unlock()`/`initCtx()` has run (iOS Safari silently discards it otherwise).

## 7. Progression, Skill Rating & Unlockables

**Two separate currencies.** XP/levels are the time-invested track; the skill tier is the how-good-are-you track. They never substitute for each other.

| | Experience / Level | Skill Tier |
|---|---|---|
| Driven by | XP | ranked μ |
| Earned from | **every** match (solo + PvP), quests, achievements | PvP, and solo at an **earned** difficulty (Pro/Cyber) |
| Direction | monotonic — never decreases | up and down |

- **Rating** (`src/rating.ts`, shared client+server): TrueSkill-style Gaussian pairs, replacing the old fixed-delta ELO. Each profile carries **two**:
  - `mmrMu`/`mmrSigma` — hidden MMR, moved by every match played on **ranked-legal rules**, solo included — a match whose rules or sonar unrank it moves NEITHER estimator (it was not played on the game the ratings describe), and Practice and Split Screen never reach `recordMatch` at all. An earned-difficulty solo is the one thing that displays as un-ranked and still feeds this: it moves no visible TIER, but it is what keeps the AI adapting and the pre-match odds honest, and none of it is ever rendered. Drives the pre-match win prediction, the XP surprise multiplier, and the recommended AI difficulty. Never rendered as a number; only ever sent to the profile's own device.
  - `rankMu`/`rankSigma`/`rankedGames` — drives the visible tier. Moved by PvP **in a venue that rates it**, and by a solo match at a difficulty the player had to **earn** (`RANKED_SOLO_DIFFICULTIES` = Pro, Elite, Cyber, Chaos). **Rookie never counts**: it is open from the first match, so placing against it would be a formality and a tier badge would stop meaning anything. A solo result weighs less wherever it lands — the lighter `SOLO_UPDATE` μ step and the `SOLO_MU_CAPS` ceiling, so farming an AI converges on that rung and stops well short of the top of the ladder. Those caps are **data, not a formula**: `anchor + AI_ADAPT_BAND` worked with three rungs and collapses with five, handing Elite, Cyber and Chaos one identical ceiling and making the three top rungs interchangeable for rank farming. Each value now sits 0.1 under a tier floor — Rookie 25 (`START_MU` exactly, so farming the open rung from a standing start moves nothing), Pro 30.9 (tops out at Master), Elite 33.9 (Grandmaster), Cyber and Chaos 36.9 (Legend) — so **Legend is the solo ceiling and Cyber Overlord (37) is only ever reached through PvP**, and `AI_ADAPT_BAND` goes back to being purely a gameplay-adaptation range. σ converges at the *same* rate as a duel's, deliberately: placement counts observations, not opponents, and shrinking it slower would land a solo player on "5/5" and still unranked. Note the standing trade-off (§5) — solo stats are self-reported, so a modified client can forge them; that was the reason this track was PvP-only, and counting earned solo difficulties accepts it knowingly, bounded by those caps. **CASUAL is the PvP mirror of Rookie**: a table in that room pays XP and moves hidden MMR and never the visible tier (`RoomDef.ranked`, `roomCountsForRank`, gating `ranksThisMatch` and not `ranked`), because a duel there is still a real human on ranked-legal rules and the odds and the queue are better for having watched it. Its own description has said so in seven locales since the room shipped — *"Any rank welcome. Play for the game, not the ladder."* — while the server rated it like any other bracket; the copy was right and the code disagreed. The venue reaches `recordMatch` from the live ROOM and never from a payload, because a client-named `casual` would be a free way for a losing player to dodge the rating loss; where there is no room left to ask, the match rates as it always did, which is the safe side (refusing on absence would silently stop counting a stock-rules duel in `elite` whose room was reaped before a retried POST landed). **`DEFAULT_VENUE_ROOM` had to stop being `casual` for any of this to be safe**: the name was carrying two unrelated jobs, "the ungated bracket" and "where a table with no venue lives", and unranking one would have taken the ladder from every invite-code duel, every older bundle and every table the test harness seats. It is the hidden `_default` room now — unlisted, ungated, spectator-permitting so the lobby's `venueRoomId || DEFAULT_VENUE_ROOM` keeps the watching toggle — and Casual is somewhere a player walks into and chooses.
  - **Each estimator rates against its own counterpart.** `duelStartRatings` samples BOTH pairs per seat, and `recordMatch` takes the opponent's `mmrMu/mmrSigma` for the hidden update and their `rankMu/rankSigma` for the visible one. One pair used to stand in for both — the hidden one — so the ladder step was measured across two scales. That is not a rounding error, because the two diverge by design: solo moves `mmrMu` and never `rankMu`, `SOLO_MU_CAPS` caps one while `AI_ADAPT_BAND` moves the other, and a match that is `ranked` but not `ranksThisMatch` moves the first and not the second. Against a Legend-on-the-ladder, ordinary-in-MMR opponent an upset win was worth 0.53 μ where it should be 1.21 — better than a fifth of a tier band, on one match, always in the same direction. Nothing was back-filled. Note that a fixture setting both pairs equal cannot tell which one was used, which is why `tests/duelRecord.test.ts` grew `seedSplit` beside `seedLadder`.
  - Prediction: `P(win) = Φ((μₐ − μᵦ) / √(2β² + σₐ² + σᵦ²))`, β = 4.1667, τ = 0.0833, start μ=25 σ=8.33, σ floor 0.6. `erf` is approximated in-module — **no new runtime deps**.
- **AI anchors**: the five difficulties are rating anchors (Rookie μ20, Pro μ24, Elite μ30, Cyber μ33, Chaos μ36, σ=0.5) rather than parameter sets. This is why *no per-difficulty XP or rating table exists anywhere* — difficulty is encoded in the anchor, and surprise falls out of the math. It is also what makes "a harder rung always pays more XP" true by construction rather than by a table: the anchors are monotone and adaptation preserves their spread, so `winProbability` is strictly lower against a harder rung and both surprise multipliers rise as it falls.
- **Adaptive difficulty** (`effectiveAiMu`) is **asymmetric**. Upward it tracks `AI_ADAPT_STRENGTH` = 0.6, bounded to +`AI_ADAPT_BAND` (7 μ), so a strong player genuinely outgrows the low rungs. Downward it tracks **fully** (`AI_ADAPT_DOWN_STRENGTH` = 1, band 20). Partial tracking leaves a residual gap of `(1 − strength) × deviation`, which is fine above average and compounding below it: a player losing every match to Pro fell to μ13 while Pro stalled at the band edge of 18, so their odds went **50% → 22%** and each further loss widened it. **The ladder must never get harder because you are losing.** The spread (Cyber − Rookie = 11 μ) is preserved exactly at every skill level either way. The **effective** μ is what prediction and XP key off — it is the strength actually faced, so the odds shown are honest — while the solo μ cap stays pinned to the **base** anchor (capping at a target that rises with the player would be circular and let solo farming lift μ without limit).
- **AI competence** (`competenceForMu` in `game/physics.ts`): the effective μ collapses to one scalar `c ∈ [0.05, `MAX_AI_COMPETENCE` = 0.78]` driving every AI parameter (reaction time, paddle speed, aim error, wall-bounce reads, lapses), so difficulties are monotonic by construction. The dominant term is `contactError` — the aim error still present at the moment of contact — because the paddle catches anything within ~0.147 of its centre. **Per-rally, not per-tick**: the AI decides how it reads a ball once, as the ball crosses the net, and lives with that read. Re-rolling error every tick averages out to a perfect aim over a long flight, which is precisely how the pre-rewrite AI became unbeatable (everything above Rookie returned **100%** of balls; solo was mathematically unwinnable). The curve is knots at the five anchors — `(12, 0.05) (20, 0.36) (24, 0.49) (30, 0.66) (33, 0.72) (36, 0.78)` — flat at the clamp above the top anchor, so an adapted Chaos plays the ceiling and never past it. Measured return rates for an average player are Rookie ~72%, Pro ~79%, Elite ~87%, Cyber ~89%, Chaos ~89%. **The ceiling moved UP with the five-rung ladder, and that is a deliberate reversal.** It had come *down* from 0.9 to 0.66 because an adapted Cyber returning 93% of balls made the top rung a lottery on the AI's own error — a real critique, and the reason the new ceiling is 0.78 rather than back at 0.9. Players reported the whole ladder too easy, and two new top rungs need headroom above the old Cyber to be distinct at all. `tests/physics.test.ts` simulates rallies through the real collision code to keep the reversal honest; **no difficulty may ever return ≥93% of balls**. Note that return rate SATURATES near the top: Cyber and Chaos measure within sampling noise of each other on this metric, and their real separation is aggression, serve pace and the anchor each is rated at — which is why the ladder-ordering test asserts Chaos on a looser bound than the rungs below it rather than pretending the difference is visible here.
- **Spin reading** (`spinRead`, capped at `MAX_SPIN_READ` = 0.85 so nobody is exempt): the AI feeds its own read into `predictLanding`, so a weak AI expects the plain mirror angle off a wall and a strong one expects the kick. Rolled **per rally** like every other read. Note the honest limitation of the impact-only model: spin only moves the AI's prediction *when a wall is actually struck*, so it is a narrower lever than a flight-curve model would be, and whether a given mis-read helps or hurts the player depends on the geometry. It is tested as prediction error (`predictLanding(ball, read)` vs the truth), which is geometry-independent, rather than as a return-rate penalty.
- **Difficulty styles** (`AI_STYLES`): strength is `c`; *style* is volatility (competence swing between rallies) and aggression (how hard it plays for the corners). **`chaos` is a revived name, and that needed a migration.** It was once retired — it sat between Pro and Cyber in rating but was defined by volatility rather than strength, so the ladder read as four rungs with three real difficulties — and `normalizeDifficulty()` mapped a stored `'chaos'` to `cyber`. The five-rung ladder gives the name back at the TOP, where strength is the anchor (μ36) and volatility is once again its style. A legacy `matches.difficulty = 'chaos'` row left alone would therefore have started rendering as the hardest opponent in the game, a match its player never played — so the one-shot `chaos_relabel_v1` rewrites those rows to `cyber`, what the retirement map already said they meant, **before** the name changes hands, which is what let the map itself be deleted. It runs after `ranked_backfill_v1`, which classifies legacy rows from mode + difficulty and must judge them under the old meaning.
- **Mode asymmetry** (PvP is always heavier than AI, on both tracks): solo uses a 0.35× μ step, half the σ shrink on hidden MMR, and a **cap** (`soloMuCap`, backed by the `SOLO_MU_CAPS` table above) so farming one rung converges on it and stops. The cap has been wrong twice, in opposite directions, and both are worth remembering. It was first the **base** anchor, which froze the whole early game: every player starts at μ25, which was exactly Pro's base, so beating Pro moved μ by nothing at all while losses moved it freely down — the hidden rating could only ratchet **downward**, and since prediction, the XP surprise multiplier and the AI's own upward adaptation all key off this μ, none of them could ever reflect a solo player improving. It then became `anchor + AI_ADAPT_BAND` — "the hardest that difficulty ever plays" — which was right for three rungs and collapses at five, because the Overlord clamp catches Elite, Cyber and Chaos together and farming the Master-tier rung would carry a player to Legend exactly as fast as farming the hardest thing in the game. A **constant per difficulty** is the invariant that survived both: one derived from the player's own μ would chase them upward without bound. What changed is that the constants are now chosen against the TIER FLOORS rather than derived from the anchors.
- **Solo XP is shaped by momentum and fatigue** (`soloMomentum`/`soloFatigue`/`soloAdjustedXp` in `rating.ts`, applied only inside `recordMatch` — a client still never sends an XP amount, and PvP is untouched). `soloXp = clamp(matchXp × momentum(w) × fatigue(n), XP_FLOOR, SOLO_XP_MATCH_CAP)`. **Momentum** ramps with consecutive solo wins, concave and saturating, so each win in a run pays more than the last by less than the last did; `w` is the streak the player CARRIES IN (`player_mode_stats.winStreak`, read before this match's own bump — the same walked-in-on convention the rally carry uses), which is what makes a loss ENDING a long run pay more than an early one, since the multiplier applies to losses too before the streak resets. **Fatigue** decays with solo matches already recorded this UTC day (`daily_solo`, bumped inside `recordMatch`'s one transaction and only on the unstamped path, so a replayed `matchKey` no more double-counts a day than it double-pays), floored well above zero: same-day solo grinding trends toward reduced efficiency but never toward nothing, which is how "solo cannot be farmed at full efficiency" became arithmetic rather than a rule to remember. The **cap is a constant** — however long the streak, no solo match pays more than it — while `XP_FLOOR` survives underneath, so "every match is progression, levels never regress" keeps holding: fatigue attacks the multiplier, never the floor. The decay is deliberately gentler than the ramp, so a real win streak still out-earns the fatigue it accrues; fatigue is there to tax streak-LESS grinding.
- Both seats of a duel are rated against the pair of ratings as they stood **before either result was written** — the relay records seat 0 first, so reading the opponent's profile inside that loop gave seat 1 an opponent that had already absorbed its own win, and the difference fell the same way in every ranked duel. **TrueSkill-2 signals** (the `performanceWeight`) are applied to PvP only and only from data the relay owns (`room.scores`, `room.maxRallyInMatch`): margin of victory and rally quality, bounded to a 0.5–1.5 weight. Solo stats are self-reported (client-authoritative physics) and feed XP only — never rating.
- **Tiers**: `unranked` until **`PLACEMENT_GAMES` (5) ranked games and σ ≤ `PLACEMENT_SIGMA` (4.0)**, then keyed on `rankMu` — Rookie <19 · Contender 19 · Vanguard 22 · Ace 25 · Master 28 · Grandmaster 31 · Legend 34 · Cyber Overlord ≥37. **The top rung reads as a POSITION rather than a name** — `#1` through `LADDER_TOP_N` (100), counting down — because it is the one rung with nothing above it, so "Cyber Overlord" is a word everybody up there shares and says nothing about which of them you are. It is a DISPLAY, not a definition: reaching Overlord is still `rankMu ≥ 37` and nothing else, `tierFor` stays a pure function of one player's own rating, and nobody's tier moves because somebody else played. Making the headcount decide the tier was the alternative and it is worse twice over — it would put the whole player table inside `tierFor`, and on a server with fewer than a hundred ranked players it would promote every placed player to the apex. An Overlord outside the top 100 falls back to the name. **The number has to be the number the leaderboard prints**, or a badge reading #12 beside a Ranks page reading #7 is worse than no badge: `getLeaderboard`'s `rank` is not a count but a dense JS counter over a filtered, ordered scan, so `db.ladderPosition` mirrors its filters — uninitialized profiles and the seeded bots, which are pre-placed and would otherwise push every human down by the whole roster. **The placed test is part of the ORDER and not just the filter**, which is the half that was wrong first: the board LISTS an unplaced player who has started placement and sorts them BELOW every placed one, so "above me in mu" and "above me on the board" are different sets — four games in, an unplaced player can hold a mu above an Overlord's and still rank under them, and counting on rating alone reported a position too large for exactly the players the number is for. The count also excludes the row's OWN id, because inside `recordMatch` the rating has moved in memory while the stored row still holds the pre-match value: after a LOSS that stored self satisfied `rankMu > ?` and the player was counted as standing above themselves. Ties needed an order that did not exist: two rows on the same rating sorted arbitrarily, so the board could reorder them between two refreshes, and `p.id ASC` now sits under every board's sort key so both answers come from one. The query is gated on the row being one the board would LIST and not merely on the tier — an uninitialized profile is placed and rated like any other row, takes 'overlord' from `tierFor`, and was handed #1 for a ladder it does not appear on. **That gate is about correctness and buys nothing on cost, which is the thing it was first believed to settle.** The reasoning was that a scan running only for the top rung runs for a handful of accounts — true, and beside the point, because the relay's hot path is `queueCandidate` and a QUEUED player on the top rung is one of that handful. `sweepQueue` rebuilds its candidate list once per pairing, so a sweep asks for every queued entry N+1 times every two seconds, synchronously, on the event loop. The repair is not a cheaper count nor an index to serve it: `queueCandidate` and `sendMatchPrediction` want two floats and were being handed a whole profile — four queries, a conditional write and the count — so they read `db.matchmakingRating` instead and the derivation is simply not on that path. `newRating()` is the fallback for a row that is not there, byte-for-byte what `getProfile`'s lazy mint produced, so nothing about pairing moved; the sweep also stops minting a player row as a side effect of looking at the queue. **A field derived from the WHOLE table does not belong on an object eleven call sites read for other reasons** — gate it, and then keep the paths that never wanted it away from the object entirely. It is computed in `readProfile`, the funnel for eleven of the twelve doors a profile reaches the client through, and again inside `recordMatch`, which is the twelfth: that one loads the profile BEFORE applying the match and hands the same object back as `MatchEndResult.profile`, so left alone it would report the pre-match number — and the win that carries somebody into the top 100 is the exact moment anyone is looking at it. The relay has a third moment of the same kind: `recordRoomMatch` writes seat 0 before seat 1, so it buffers both results and re-derives the position after both commit rather than pushing inside the loop. And the CLIENT can still throw that correction away — `applyMatchResult` drops a `matchKey` it has already shown, which is right about confetti and wrong about a profile — so a duplicate is judged by SOURCE: the relay's copy is read after both seats are committed and still installs its profile, while the page's own POST, which records one seat and cannot know the other, is dropped as before. Judging by arrival order instead reads well and fails in the mirror case. Nothing refreshes the number while the menu sits open, either — the session heartbeat never reads a profile — so `RanksPage` spends its arrival on both the board and `fetchProfile`, or the header holds #7 beside a page that just fetched #9. Deriving them together is what stops an arrow with no direction, or a direction with no arrows. `'none'` covers both "this match did not rate" and "it rated and landed where it started" — from the player's side those are the same fact, and one glyph says it. - **XP**: `35 play bonus + points×12 + min(maxRally, 25)×6 + 40 win bonus`, scaled by the surprise multiplier (win `0.6 + 1.4×(1−P)`, loss `0.40 + 0.55×(1−P)`), ×1.5 for PvP, floor 45. The rally term is capped by `RALLY_XP_CAP` so an unbroken match-long run cannot pay a windfall. **Never negative — levels cannot regress.** Every figure here is a named constant in `src/rating.ts` (`XP_PLAY_BONUS`, `XP_PER_POINT`, `RALLY_XP_CAP`, `XP_PER_RALLY`, `XP_WIN_BONUS`, `XP_FLOOR`); quote the names when you restate this, because the numbers have moved twice and this line did not move with them.
- **A rally streak belongs to ONE player.** It counts that player's own consecutive successful returns and breaks **only when THAT player fails to return one** — the opponent missing is a point you won, not a streak you lost. So a streak runs across points, and across **matches**: a match ending is not a miss. The serve is not a return (the receiver's return OF it is the receiver's first, and the server's run resumes on their first return of that). What this replaced was a single counter that BOTH players incremented — your own paddle hit and the opponent's ball arriving back — and that reset whenever EITHER of them scored, so a player's rally number was mostly a statement about their opponent. The rule lives in three places that must agree: `countReturn`/`breakStreakOnPoint`/`startMatchStreaks` in `server/room.ts` (the relay, and imported wholesale by the P2P replica so it cannot drift), and `src/game/streaks.ts` for the client, which is the only authority in a solo match. **The run is stored, not remembered**: `player_mode_stats.currentStreak`, per mode, so it survives a reload, a different browser, and a different room. It is the one column there that is **assigned** rather than added or maxed, so it is the only one that needs ORDERING: idempotency tells two matches apart but does not sequence them, and a result that failed to POST sits in the on-device queue through a whole replay and lands afterwards — restoring a run the replay had already broken. **Two mechanisms, because there are two questions.** An age orders a write against writes from OTHER moments — a match replayed off the on-device queue days later says so and loses to what overtook it. It cannot order two writes from the SAME browser correctly when their own network round trips differ: an age never counts a request's own time on the wire, so whichever of two writes happens to have the FASTER trip can reach the server "later" in stamped time even though it was decided first — a serializing queue only closes this when one write is actually queued behind the other, which cannot help a match parked before a reload and replayed after it, since the page that would have queued it is gone. So a second signal doesn't serialize, it **numbers**: `nextRunSeq()` (`src/net/runChain.ts`) assigns a position in this browser's own chain once per event, at the same moment as `endedAt` and before anything is sent, and PERSISTS it in `localStorage` — so a payload parked and replayed after a reload keeps the exact number it was decided at, comparable to whatever this same browser assigns afterward with no regard to how long either request's own trip takes. `chainId`/`runSeq` ride on every run-assigning payload as a pair; same `chainId` and a higher `runSeq` means later, however the wire behaved, and a different chain (or none at all — an older bundle, or the relay's own writes) falls back to the age. Reading, incrementing and writing that counter back is not atomic across TABS, so two tabs on one device can rarely read the same starting value and report the identical next number for two different events — a tie the server breaks with the age rather than always favoring whichever tab's request happens to arrive first, which was a real bias, not a coin flip. A failed **write** (quota, a private-browsing cap) is answered with a freshly random `chainId` rather than the incremented-but-unpersisted number the read produced: reads and writes fail independently, so returning that number would look fine once and then repeat identically on every call for the rest of the session, since the next read finds the same un-incremented row — silently reintroducing the exact network-timing bug this exists to remove, for every write from that point on. Deliberately not a credential: a modified client could already forge any field a match payload carries, so this adds no reach and needs no verification, only a type check so a malformed value cannot reach a SQL bind. Neither mechanism replaces the other. **Every writer that ASSIGNS the run shares one ordering mechanism**, or the ones that do not are simply stamped on arrival and outrank whatever overtook them in flight — `/api/match/record`, `/api/practice/record` and `/api/profile/me/streak` all carry it, and the relay's own writes happen as they happen. The ordering key is an **age, never a clock**: `endedAt` is stamped when the run reached that value and `clientNow` is read as each attempt goes out, so the server takes their difference — two readings of one clock, free of whatever offset that clock carries — and places it on its own timeline (`player_mode_stats.streakAt`). Comparing a device's absolute clock to the server's breaks in **both** directions and clamping one end fixes only half: a phone running fast parks the row in the future and freezes the column until reality catches up, a phone running slow has every result it ever sends look older than what is stored and be ignored the same way. A **negative** difference is read as maximally old rather than as "just now": it means the clock moved between the two readings, so the elapsed time is unknowable — and "just now" is the reading that would let a queued result overwrite the newer one that overtook it. An older result still gets its additive half (it happened, and it is owed that) and is ignored for the carry **and for the per-mode win streak**, which accumulates into a `bestWinStreak` maximum and would otherwise be inflated permanently by an old win landing after a newer loss. The trade is the mirror case — an old win belonging to an unbroken run is not added — and that is the side to be wrong on. No age means "just now". — the relay seeds a seat from it at `create_room`/`join_room` rather than taking it from the client, since it decides what the match is rated and paid on. **The client still needs its own copy** (`CarryStore` in `src/game/streaks.ts`), because the profile only learns a match's ending run when that match's POST comes back and Play Again is a synchronous button: read from the profile alone, a replay opened on the run from *before* the match just played — discarding a run a winning point had left intact, then reporting the smaller number back over the correct one. What this page last saw for itself wins; the profile is the fallback, and the only source after a reload. It is deliberately never cleared, since a heartbeat-refreshed profile can arrive before the match POST does. **A carried run is a real run, and it is not work this match did** — so `MatchEndPayload` carries three numbers, because they answer three different questions. `bestStreak` is the peak the run reached (opening on whatever was carried in), which is what the career best, the mode best and the rally achievements are about. `endStreak` is where the run stands when the match ends, which is what the next match starts from. `earnedStreak` is how much of the peak was built HERE, counted from zero — and it is the only one anything is **paid or rated** on: `matchXp`, `practiceXp`, `performanceWeight` and **daily rally tasks**. **Every exit from a match reports where the run stands** — the final whistle, the Practice Wall's own report, quitting an unfinished match, the HUD's Reset (both locally AND, through `POST /api/profile/me/streak`, to the server — carrying the run into the restarted match is only half of it, and without the other half a reload put the pre-Reset run straight back), and **an abandoned duel** — which is decided by nobody, so `recordRoomMatch` never runs and the relay writes both seats itself from `room.streaks` (`db.recordDuelStreak`, the room's own way to say what `reportStreak` refuses a client). The survivor counts as much as the leaver: they are bounced to the menu just as abruptly and their run is just as real. Only a finished match reports itself, so without the others a player who carried a run in, missed and walked out was seeded from the stale carry next time: the miss simply undone. Paying on the peak instead is a farm with no work in it at all: carry a run in, open the Practice Wall, leave without touching the ball, collect for it again — every day, up to the daily cap. The relay derives its own pair (`Room.earnedStreaks`/`earnedBests`, reset to zero by `startMatchStreaks` while `bestStreaks` opens on the carry) rather than believing the client's, and the server bounds every one of them by the peak: neither what a match earned nor where its run ended can stand higher than the run ever reached. `RALLY_XP_CAP` stays on top of that as a ceiling on the rally term, so even an unbroken match-long run cannot pay a windfall. Thresholds were rescaled by **0.72** in the same release (measured, not assumed: dropping the opponent's hits halves a point's count while surviving points lengthens it, and the two do not cancel to a half) — missions 8/15/40 → 6/11/28, achievements 10/25/50/100/150 → 7/18/36/72/108, `minRally` 10/25 → 7/18, `XP_PER_RALLY` 4 → 6, `performanceWeight`'s `/20` → `/14`. `wipe_v4` ships with it, because nothing banked under the old counting is comparable to the new.
- **Stats are kept per mode as well as pooled** (`player_mode_stats`, keyed `(playerId, mode)`): matches played/won/lost, points, aces, best streak, the run still going, and a win streak that a loss in another mode cannot end. Solo, duel and practice each get a row; **Split Screen gets none**, since only one of the two people at that phone has an account to write to. The career totals on `players` are unchanged and still pool everything — they answer "how much have you played", which is a different question. A separate table rather than four times the columns on `players`, whose `upsertProfile` is a hand-written INSERT with a column list, a VALUES tuple, a DO UPDATE SET and a positional argument list that all have to agree. **The bump goes in the same transaction as the profile, the match row and the `recorded_matches` stamp**: it is the one write in `recordMatch` with no ceiling of its own — mission progress caps at its target and the profile is upserted whole, but matches played and points only ever add — so a bump that landed while the match went unstamped would be counted again by the client's retry, and again by the one after that.
- **Level curve**: `band(L) = 250 + 60×(L−1)` (~2–4 matches per level). The old `120 × L^1.6` had a 120 XP first band that a single match overshot outright.
- **Match rules** (`src/matchRules.ts`, shared client+server): six physics multipliers (paddle/ball size, min/max ball speed, serve angle/power — 1 is stock) plus four presentation flags (sonar, telemetry, quick chat, auto-serve seconds). Chosen in the MainMenu's pre-match sheet for a solo, practice or split match and **in the lobby for a duel** — the same `MatchRulesPanel` in both — fixed once the first ball crosses the net. Each physics rule carries a `ranked` band; tuning inside it keeps the match rated, pushing past it pays XP only. The **sonar** flag rates too — see §1 and §3 — while telemetry, quick chat and auto-serve never do. `normalizeRules()` clamps and snaps everything arriving from a client or from storage, and pins `ballSpeedMin` under `ballSpeedMax`; `normalizeRoomConfig()` does the same for a duel's terms.
- **Every match is progression.** `matchXp` carries an `XP_PLAY_BONUS` paid for finishing a match at all, the loss multiplier floors at 0.40 (was 0.20) and `XP_FLOOR` is 45 (was 15). A loss used to pay the bare floor — about 25 losses to a level, which reads as nothing. It is now 6–8.
- **Daily streak**: consecutive active days tracked on the profile.
- **Daily missions** (surfaced as **Active Tasks**) are a **dealt hand, not a fixed list** (`src/game/missions.ts`, shared client+server). Each UTC day a player is dealt `REGULAR_SLOTS` (3) from a 12-strong regular pool plus **`ELITE_SLOTS` (1) from a 6-strong elite pool** — three, not five, because a short list is one a player reads and because the slots have to leave the pool spare room to deal a replacement from, chosen by a seeded shuffle of `(playerId, dayKey)` — deterministic, so it survives a restart without being stored, and two players get different hands. State is server-owned across three day-keyed tables — `daily_mission_slots` (what you hold), `daily_missions` (progress and claims), `daily_rerolls` (what you have spent) — plus `recent_missions`, which is deliberately **not** day-keyed (see below). The hand size is a constant but a player mid-day holds whatever they were dealt that morning, so `trimSlots` retires any surplus on read: lowering `REGULAR_SLOTS` has to take effect on the list they already have, not just tomorrow's. **A task is only dealt if the player can actually play it** (`missionRequires`/`dealablePool`, filtered in `ensureSlots` and `fillSlot`): `elite_cyber_3` asks for three Cyber wins, pays 600 XP and a permanent theme, and was dealt to players who had not opened Cyber — told to go and beat an opponent the menu would not let them select, against a single elite reroll a day. Note the two spellings, because missing either leaves half the problem: a duel task says so through `mode` (`elite_duel_3`) OR through `type` (`mission_multi`, which carries no `mode` field). The filter may never shrink a pool below its slot count — trading an impossible task for a missing one — so the worst case, an account with no achievements at all, is asserted directly rather than assumed. The read of the achievements column is deliberately NOT a `getProfile`, whose lazy mint would create an account as a side effect of looking at a task list. `sweepClaimed` runs beside `trimSlots` and refills any slot still holding an **already-paid** task, or one the player cannot play — unlocks only ever accumulate, so that second case is only ever a slot filled before the deal was filtered — the auto-reroll fires at claim time, so a task claimed under older rules is never revisited, and the player cannot shift it either (a claimed task refuses both a reroll and a second claim). A task that is finished but *unclaimed* is deliberately left alone: that is the reward waiting to be collected. The one-shot `tasks_reset_v1` migration cleared everyone's hand once, since a half-finished five-task hand is not something the read-time repairs could turn into a sensible three. Progress advances only inside `recordMatch`, and only for the missions actually held — advancing the whole pool would let a rerolled-away mission come back half-done. **A rally task counts the run EARNED in the match, never the peak it reached**: a streak carries in, so reading the peak let a task dealt or rerolled onto a player already on a long run finish itself on the next recorded match with no ball returned — at its worst paying an elite task's 600 XP and its permanent theme for nothing, and breaking the from-zero rule below. The honest cost is that a run spanning the deal boundary counts only the part built after it, which is the safe side of the trade. `POST /api/missions/claim` stamps `claimedAt` before paying; the primary key makes a replay a no-op. This replaced localStorage missions claimed via a client-chosen `xpDelta` on `PUT /api/profile/me`: clearing site data re-armed them all, and the endpoint could be called in a loop (verified: level 1 → 15 in ten requests). **Never add a route that takes an XP amount from the client.**
- **Rerolls**: 5 regular and 1 elite per UTC day, spent independently per tier. A completed mission cannot be *paid*-rerolled — nothing to gain, a reward to lose. **Claiming one auto-rerolls its slot for free**, unlimited and charged to neither allowance: the allowances exist for missions you did not want, and finishing one is the opposite of that. Both allowances live in a `dayKey`-keyed row, which *is* the expiry mechanism: a new day means a new row, so unused rerolls never bank up and a partly-spent day never carries over.
- **Tasks repeat, and a dealt task always starts from zero.** `fillSlot()` deals anything that is not currently held and was not among the last `RECENT_DEAL_MEMORY` (3) deals of that tier, tracked in `recent_missions` — keyed by an explicit per-(player, tier) `seq` counter rather than a timestamp, because a whole hand is dealt in one go and would otherwise share a stamp, leaving the window's edge to a tiebreak. The table is **not** day-keyed: a task finished last night should not be first in line this morning. Two rules this replaced, both reported as bugs:
  - *One-and-done*: a finished task used to be barred from being dealt again that day, so a productive player worked through the twelve-strong pool — about four duels at five slots — and a claim then had **nothing** to hand back, leaving the finished task sitting in its slot marked "claimed". A repeating pool cannot run out. The `RETIRED_SLOT` fallback stays as a backstop (blanked, never deleted — `ensureSlots` reads "no rows for today" as "not dealt yet", so removing the last row would deal a whole fresh day), but it is now effectively unreachable.
  - *Carried progress*: progress is stored per `(player, day, task)`, so a task dealt back into a slot arrived holding whatever it collected the last time it was held — a rerolled "Point Machine" turning up at 21/25, which is a reward for nothing. `dealMission()` clears the row as the task enters the slot, so every deal is a fresh start; with repeats now allowed this is what stops one arriving already finished and claimed.
- **Elite missions are the permanent-unlock track.** Their XP is a daily reward like any other, but the first time one is ever completed it banks a row in `elite_completions` — deliberately **not** day-keyed — which unlocks a theme for good. Repeating it later pays the XP again and grants nothing further. `profile.eliteUnlocks` carries these to the client, where `isCosmeticUnlocked` reads them.

The two modes branch EXPLICITLY rather than flipping one direction: a dark UI raises the card off a dark page, a light UI does it by making the card whiter than an already light page while its dividers go down — flipped, it lands dark ink on a darkened card and every light cosmetic fails contrast.
  - **Semantic status colours do not follow the cosmetic**, they pick a RAMP. Green means won and red means lost; a cosmetic recolouring those changes what the screen says. But a set tuned for a dark ground fails on a light one, so `mode: 'dark' | 'light'` selects between two curated ramps and the hue stays put.
  - **Two floors, held by `tests/cosmetics.test.ts` over every cosmetic and every pair.** READABLE: the ink ratios `index.css` states as its contract (7:1, 4.5:1, 3:1, and 4.5:1 for the accent's own ink, which is PICKED per cosmetic rather than assumed — a yellow accent and a navy one need opposite answers). DISTINCT: ≥0.08 mean OKLab across the seven colours a player reads a cosmetic by. That floor is calibrated, not picked — when it was set the closest pair sat at 0.034 against a median of 0.17, seven pairs failed, and the next step up failed eighteen. It is a MEAN deliberately: a minimum calls two cosmetics distinct the moment any single swatch differs, which is exactly what had shipped, with `retro-crt` and `monochrome-noir` agreeing on white-on-black everywhere and differing in one glow.
  - **Locked cosmetics are ABSENT from the picker** — no tile, no name, no swatch, not in the DOM — and it lives in the Profile, not Settings, because the choice is not a preference about this phone. What that replaced listed all twenty with the fifteen locked ones dimmed and captioned with their cost, previewing their colours in three chips, which gave away the thing the reward IS. The consequence is that the unlock moment is the only time a player meets one, so the toast that fired for six elite missions now fires for every route in, diffed off the profile.
  - **Ids are read forward, never migrated.** `LEGACY_COSMETIC_IDS` + `normalizeCosmeticId` map a renamed id (`tennis` → `arena-pro`), because the equipped value is persisted in `localStorage` AND in `players.cosmetic`, so a rename is not a compile error — it is a player quietly losing a cosmetic they own. **Never rename `MissionDef.unlocks`**: that is the value banked in `elite_completions`, and the unlock check compares against it rather than against the cosmetic's id. The two look like they must agree and they do not; rewriting that ledger to keep them matching would take back permanent unlocks to fix a spelling.

- **A shutout is a clean sheet AND a match length** (`SHUTOUT_MIN_POINTS` = 5 and `isShutout` in `src/matchRules.ts`, beside `WINNING_SCORES` because the floor is a length). The floor exists to exclude the 2-0 that was never played to the end: the relay records an abandoned duel at the STANDING score (§5), so without it, getting somebody to walk out early would pay like holding them scoreless over a full match. What it costs is the whole first-to-3 format — every scoring path stops at `winningScore`, so a 3-0 there IS the entire match and still falls short — and first-to-3 is open from the very first match. **That is a real trade, so every description that depends on it states the length out loud.** It did not: the rule was three copy-pasted expressions (the `shutoutsWon` counter, the achievement triggers, the daily tasks) with the number written down in none of the copy, while five achievements, two daily tasks, the entire Dominion branch and the `flawless-white` theme all said "without conceding a point" — true, and only half the requirement. A player winning 3-0 against Cyber over and over moved nothing and was told nothing, and "concede" was doing none of the explaining. One definition now, quoted by the copy and pinned by `tests/achievements.test.ts`. `shutoutsWon` was also added by `addColumn(... DEFAULT 0)`, so every match played before it existed counted for nothing and there is no path back — the counter is only ever incremented by the match in hand — hence the one-shot `shutout_recount_v1`, which recounts from `matches` as **`MAX`, never an assignment**: `insertMatch` trims that table to the newest 500 rows per player, so a straight recount would rob exactly the accounts that have played the most. `shutout` itself reads the counter rather than the match in hand, the same way the rally rungs read `highestRally`, so a feat performed before its gate could open is banked rather than lost.
- **Achievements are a branching tree AND the progression gate** (`src/achievements.ts`, shared client+server). **Eight branches, 50 nodes.** Five are open from the first match — Foundation, Rally, Ladder, Duel, Craft — and **three are concealed trees the player discovers**: Ascent (the ranked tiers; opens on a first duel), Dominion (streaks and shutouts; opens on a first shutout), Devotion (the long haul; opens at level 5). A concealed branch's tab is a lock with a hint (`BranchDef.gate`/`gateHintKey`); everything inside it is invisible until it opens — the branch itself is the silhouette. Beyond the parent rule, deep rungs can carry an `AchievementGate` — a minimum profile **level** and/or visible **tier** (`ai_pro_10` needs level 10, `cyber_10` needs Grandmaster, `points_2000` needs level 25) — checked in `isUnlockable(id, earned, ctx)`, whose `ProgressContext` argument is deliberately required: an optional one would fail open. Gating is **strict**: a parent is never granted implicitly, because auto-granting ancestors handed out `ai_rookie` for beating Pro, a difficulty the player had never beaten. Where one result genuinely satisfies a chain (a 50-hit rally is also a 25 and a 10) the triggers fire in order and each rung opens the next. Deep rungs are `hidden` — a silhouette until their parent is earned — **except a rung that appears in `UNLOCKS`, which may never be hidden**. `cyber_10` opens Chaos and was, while the solo room list printed its title beside the locked room: the two surfaces disagreed about whether the name was even a secret, so a player who read "Machine Ender" off the menu and went looking for it in the tree found `??? Hidden`. And because the tree draws `Requires {parent}` and **never** the `AchievementGate` — so a level-6 player holding `ai_pro` is told "Requires Even Contest", an achievement with a green tick two rows above — **a gated rung's own description is the only channel its gate has**, and five of them (`duel_50`, `ace_100`, `points_2000`, `streak_10`, `rally_150`) said nothing about it at all. Both rules are held by `tests/achievements.test.ts`, the second as a copy-quotes-its-threshold check: a description that stops naming its own gate fails. The counters the new rungs measure (`winStreak`/`bestWinStreak`, `shutoutsWon`, `rookieWins`/`proWins`/`cyberWins`) are **computed only inside `recordMatch`** from the result the server just accepted — a client reports a match, never a total. Achievements marked `scaled: true` — `first_win`, `shutout`, `cyber_slayer`, `duel_shutout`, `multiplayer_champ` — pay `xpReward × surpriseMultiplier`, the same multiplier the match XP uses, because the AI adapts to the player and a flat reward would pay a μ40 player the same for a Cyber win they take often as a μ25 player for one they rarely take. The award lands on `Achievement.awardedXp`. **Rally achievements stay flat on purpose**: a stronger AI returns *more* balls, so long rallies get easier as difficulty rises and scaling them would run backwards.
- **The tree gates the game** (`UNLOCKS`, `hasUnlock`): Pro is locked until you beat Rookie, **Elite until `ai_pro_10` — ten Pro wins at level 10+ — Cyber until `ai_elite_10`, ten Elite wins at level 15+, and Chaos until `cyber_10`, ten Cyber wins at Grandmaster.** A single Pro win used to open the rung above, which handed a first-session player the hardest opponent in the game before they had any feel for the middle rung; simulated at real win rates the climb now lands around match 21 at level 11 instead of match 2. **Every rung of that ladder is a win count, and nothing else may join it.** `cyber_10` used to hang off `cyber_shutout` — a hidden rung asking for a clean sheet against Cyber — so the last step of the AI ladder was a feat orthogonal to the ladder: invisible until earned, and impossible outright at first-to-3, where the match caps at 3 and the shutout floor is 5. A player who beat Cyber 3-0 several times therefore climbed nothing, saw no counter move, and had nowhere to read why. The shutout is a sibling feat now, exactly the shape `duel_shutout` already has beside `duel_10`. Worth recording is what did *not* catch it: `tests/achievements.test.ts` held a reachability walk that passed throughout, because it appends ids to a list rather than playing for them, and a "no dead ends" test that read `unlockedKeys(ancestorsOf(id).concat(id))` and then asserted the set contained `UNLOCKS[id]` — the entry it had just put there, so it could not fail in any circumstance. Both are repaired, and the ladder is now walked to Chaos through real `recordMatch` calls with a point conceded in every match, which is the assertion that goes red if a feat is ever put back on the path. First-to-10 is behind a first win, first-to-15 behind 10 matches. The ladder is walked, not jumped — which also means the win odds on the menu are odds the player has a basis to judge. Enforced **server-side** in `/api/match/record` (403 `DIFFICULTY_LOCKED`), not just hidden in the menu, since the menu is the client. **A locked option must therefore never be the ACTIVE one** — the server is right to refuse it, so the setting is what has to be corrected. Match settings live on the device and the achievements that open them live on the server, so the two drift: a wipe clears the achievements while localStorage keeps the difficulty they opened. `playableDifficulty()` / `playableWinningScore()` clamp a stored setting down to the best rung the profile has actually earned, and `DEFAULT_SETTINGS` takes its difficulty from the head of `DIFFICULTY_ORDER` rather than naming one, so the shipped default cannot itself be locked. It shipped as `'pro'` — locked until Rookie is beaten — so **every solo match a new player played was answered 403 and thrown away** (a 4xx is a verdict, not a hiccup, so it was not even queued): no XP, no missions, no history, until they happened to switch to Rookie by hand. `tests/achievements.test.ts` asserts no gate is ever locked behind something that needs it — a dead end would be unrecoverable.
- **`ACHIEVEMENT_BAND_CAP` (0.6) is what keeps progression legible.** Rewards are flat constants but level bands grow, so a value sized for the mid game lands as a windfall early — `level_10` used to pay 750 into a 790-wide band, awarding almost the whole of the level it was celebrating, and a scaled unlock times a 1.9 surprise could beat that. One budget of `0.6 × band` covers **everything a single match unlocks**, since several achievements landing together was the other route to a free level; it is measured against the level reached *after* that match's own XP applies. Level-milestone rewards are additionally held under 40% of the band they celebrate, or they feed back into themselves. Over 1440 simulated matches the only remaining two-level gains sit at levels 1–4, where the bands are narrowest; `tests/achievements.test.ts` asserts they never happen above that.

```bash

npm run build    # vite build (client) + esbuild bundle (server) → dist/
npm start        # node dist/server.cjs (production)
npm run lint     # tsc --noEmit
npm run lint:suites # every scripts/e2e-*.mjs is registered with the runner (CI runs it)

npm run test:coverage # the same suites plus the per-module coverage floors CI enforces
npm run test:e2e # browser E2E — needs `npm run build` first (see below)
```

Environment: `PORT` (default 3000), `DATA_DIR` (default `./data`). See `.env.example`.

**A session installs its own tooling, and that is a hook rather than a note to remember.**
`.claude/hooks/session-start.sh` runs on every SessionStart: it fetches the plugin marketplace,
installs the three gamedev plugins at project scope, and runs `npm install` when `node_modules` is
missing or older than the lockfile. It is idempotent — a warm container takes 0.7s and a cold one
about 11s — and it **never exits non-zero**, because a session that cannot reach GitHub is still a
usable session and these plugins are agents and slash commands invoked deliberately, so their
absence degrades nothing on its own. It warns on stdout instead, which is where to look. What it
replaced was a paragraph in `.claude/skills/README.md` asking a human to run the loop by hand,
which failed twice over: nobody reads a setup note in a file they opened for something else, and
the loop it printed had never worked on a fresh machine anyway (see that file for the missing
step). **A fresh clone therefore needs no manual setup, and anything that does belongs in the
hook rather than in a sentence somebody has to find.**

**What the hook cannot do for itself is load a plugin into the session that installed it.**
Whether an install lands in time for the listing that session was built from is not something a
SessionStart hook can guarantee, so if `/web-games:` completes nothing, the fix is
`/reload-plugins` — which applies an install to a session already open — and not a second
install. The next session starts warm regardless, since the container image is cached after the
hook completes.

**CI** (`.github/workflows/ci.yml`) runs on every push to `main` and every PR, as two
parallel jobs. `verify` is the fast one — typecheck, `npm run test:coverage`, build — and `e2e` drives
the browser suites, which cost minutes rather than seconds, hence its own job: a red one
names the broken flow instead of a broken build. `npm run test:e2e` is the same entry
point locally. Every suite gets its own free port, throwaway `DATA_DIR` and
`node dist/server.cjs` (the production entry — a suite would otherwise inherit another's
players and leaderboard), so `npm run build` is a precondition, and Chromium is resolved
from `CHROMIUM_PATH`, else a Playwright download, else a system Chrome. That per-suite
isolation is also what lets the runner hold several in flight (`E2E_CONCURRENCY`, default
a quarter of the cores capped at 4 — measured, half flaked a timing suite on a 4-core box;
`=1` is the old serial run), which is what makes running ALL of them the cheap answer
rather than the noble one. `verify` runs
`test:coverage` rather than a bare `npm test`: per-module floors on the shared pure logic,
set in `vite.config.ts` beside the reasoning, with deliberately **no global threshold** — the
components are Playwright's job, and one number would either fail on that bet or be set low
enough to measure nothing. It also opens with `lint:suites`, before `npm ci`, because that
one needs no dependencies and costs milliseconds: a file named `scripts/e2e-<name>.mjs` that
is missing from `e2e-run.mjs`'s `SUITES` is not a skipped test, it is a test **nobody knows is
not running** — it reads as coverage in review and never executes. Nothing else in the repo
can notice: `npm test` does not touch those files, `tsc` does not read them, and the runner
cannot report a suite it was never told about. A **targeted** E2E run is deliberately not
offered: a changed-file→suite map was built and deleted, because the coupling that decides it
(which suites play a match, or a relayed point) is behavioural rather than static, and every
rule anybody checked was too narrow in the direction that lets a green run hide a broken flow.
`.claude/skills/phong-ship-check` keeps that reasoning so it is not rebuilt. **A suite that
asserts old behaviour is a suite that will be deleted rather than read** — when a rule
changes, change the suite in the same commit.

**CodeQL runs for the analysis, and the ruleset that prompted it is gone.** `.github/workflows/codeql.yml` was written to satisfy a repository ruleset that held `main` to code scanning, and the episode is worth keeping even though the ruleset is not: for a while the rule was active and **nothing in the repository produced any results**, because there was one workflow and it was `ci.yml`. **A required analysis that nothing generates is not a safety net, it is a branch nobody can merge into** — a pull request sits at `blocked` with every visible check green and no failing job to point at, which is why it went unnoticed until a merge came back `blocked` where the previous one had been `clean`, and the ruleset had to be read through the REST API to find out why. The ruleset was later removed outright, so nothing gates `main` today; the workflow stays because a scan is worth having on its own, and it now reports rather than blocks.

Three things about its shape survive the ruleset and are the reason not to rewrite it casually. The **`pull_request` trigger** is what puts results on the PR head — the `push: [main]` one only ever gives the default branch a baseline, so a workflow with `push` alone would satisfy no per-PR requirement if one is ever added back. **`security-events: write`** is the permission that fails quietly: without it the upload at the end fails while the job still goes green, which is the same silent gap in a different costume, and the way to tell is that the separate `CodeQL` check posted by the code-scanning service never appears beside the `Analyze` job. And it is **advanced** setup rather than GitHub's default setup because default setup is a repository SETTING that the automation here cannot reach (403 `Resource not accessible by integration`, the same answer branch protection and Copilot settings give); if anyone turns default setup on later, this file has to be deleted in the same change, since GitHub disables one of the two rather than running both. `build-mode: none` and no `npm ci`: CodeQL reads this source directly, and putting a `node_modules` tree in front of an extractor that excludes it would add minutes to every PR for nothing.

**The rest of that ruleset could never have worked from inside the repository, and that is the transferable part.** `code_quality` and `copilot_code_review` are GitHub-side features: the Copilot rule needs a Copilot Pro subscription on the account, and without one it sits in the ruleset requesting nothing and blocking nothing — a rule that advertises "every PR is reviewed" while PRs merge unreviewed is worse than an absent one, because the ruleset reads as a guarantee. **A branch rule is only as real as the thing that reports to it**, whether that thing is a workflow in this repository or a subscription somewhere else.

**`TESTING.md` is the working guide to the suite**: what each layer owns, why a V8 coverage
report reads 0% for `server.ts` and every `.tsx` (they run out-of-process), how the floors are
set, and the standing invariants the tests exist to hold. Read it before adding a suite.

## 9. Conventions

1. **Server-side logic lives in `server.ts` / `server/`**; no keys or secrets in client code (the app currently needs none at all).
2. **Strictly normalized coordinates**: all court physics in `[0,1]` floats so every device agrees regardless of pixels or aspect ratio.
3. **Audio only after a user gesture** (see §6).
4. **Protocol changes start in `src/types.ts`** — both client and server import their message shapes from there.
5. **Icons**: lucide-react. **Styling**: Tailwind utility classes; inline styles only for dynamic canvas/theme color bindings.
6. **Keep the client origin-relative**: derive WS and API URLs from `window.location` (this is what makes dev, tunnels, and production work unchanged).
7. **Match settings are pre-match only, and in a duel they belong to the ROOM**: a solo match takes them from the MainMenu; a duel takes them from `RoomMatchConfig`, set by the host in the lobby and broadcast to both phones. The in-game Settings modal is device preferences only, and the HUD reset button is hidden in a duel — the score belongs to the room, so a local reset could only desync. Never read `settings.winningScore` or `settings.rules` in match code; read the derived `activeConfig`, or a phone will quietly play its own match (see §5).
8. **Never widen what a device may do without a live session.** Anything that spends, earns, or changes goes behind `requireActiveSession`; anything that resolves a profile goes behind `blockReleasedDevice`, or the lazy mint in `getProfile` hands a retired device a brand-new account. A new gameplay path needs the check in `server.ts` **and** at the WS upgrade.
9. **The device gate reads the platform, never the window.** No width, height, or orientation may re-enter `src/device.ts` — a window is not a device, and that is precisely the bypass it replaced.
10. **Username & avatar rules live in `src/profileRules.ts`** and nowhere else — both sides import them. Usernames enter the system only through `initializeProfile`/`changeUsername` (never via query params, match payloads, or WS messages).
11. **A user-facing string ships in all seven locales, or it is not shipped — and the dictionary and the product must agree in both directions.** `t()` falls back to English for a key a locale lacks and returns the KEY ITSELF for one nothing defines, so both failures are silent: an untranslated string renders in English, and a typo renders `menu_quickmach` to the player. `tests/i18n.test.ts` pins all three. **Parity**: every locale carries every `en` key, invents none, leaves none blank, and preserves every `{param}` English declares — 70 keys had drifted English-only before it existed. **No dead weight**: a key the product never quotes fails the suite; 47 of 333 were unreferenced, including ten theme names that had drifted out of sync with the catalogue and would have rendered the wrong words if anything had used them. Cosmetic names are back in the dictionary now that a player picks one by name, and each catalogue entry spells its `nameKey` in full rather than building it — a key assembled at runtime is invisible to the dead-weight check and reads as unreferenced. **No missing keys**: a `t()` call for a key the dictionary lacks fails too — that check found `t('you')` and `t('progression')` rendering their own key names in the HUD and the winner overlay. Note the second rule makes a test a poor place to name a key: pinning one nothing renders is how a test becomes the only thing keeping a dead string alive.

12. **Anything that shows the player the half they are not meant to see is a match RULE, and it costs the rating — and a ROOM can cost it without being a rule at all.** The blind half-court is the game; a feature that lifts it is not a presentation preference however it is spelled, and it belongs in `MatchRules` behind `isRankedRules` rather than in `GameSettings`. The two net indicators are the line: they say where the opponent's paddle is and whether the ball is over there, which is what a player on the other side of a real table can see anyway, so they are device preferences and they are free. The sonar draws the half itself, so it is a rule and it is not. A new one of these is a decision about which side of that line it falls on — make it deliberately, and if it is on the sonar's side, add it to `isRankedRules` and to `unrankedReasons` in the same commit or the pre-match badge starts lying.

    The second half is newer and is a different question. **Where a match is played can unrank it without anything about the match changing** — `RoomDef.ranked` is false for `casual` alone, `roomCountsForRank` is the predicate the badge and `recordMatch` both ask, and it gates `ranksThisMatch` rather than `ranked`, so hidden MMR still moves. It is not a `MatchRule` and must not become one: `MatchRules` feed `isRankedRules`, so a room flag put there would show up in the "what unranks this match" list as though it were physics. Three design notes used to say the venue answer was drawn by room *specifically so that* no new `unrankedReasons` case would be needed; that half is now reversed and they have been rewritten in place rather than left standing. `'venue'` sits SECOND in the ordered list, above `'sonar'`, and the order is load-bearing because the panel renders `blockers[0]` alone: on a Casual table with the sonar on, naming the sonar tells the host that switching it off restores the ladder, which is a lie. The venue cannot be changed from the lobby; the sonar can. And the badge reads the venue from `table_state`, which is about the TABLE, not from the room the player was browsing — those differ for anybody who arrived on a join key, and a badge right for the host and wrong for the guest is the failure the whole reason exists to prevent.

13. **A colour token is only real if the equipped cosmetic can publish it.** `src/index.css` declares the defaults and `cosmeticVars()` (`src/game/cosmetics.ts`) republishes them per cosmetic; a token added to one and not the other does not fail the build, it renders correctly for the default cosmetic and wrong for the other nineteen — and inside `PublicProfileModal`, which paints in a *different* cosmetic than the page around it, it renders the OBSERVER's colour on somebody else's profile. `tests/cosmetics.test.ts` reads the stylesheet and fails on the mismatch. Two corollaries. Never express one token in terms of another (a `color-mix()` over `--color-ink` inside `@theme`): custom properties are substituted where they are declared, so such a token resolves against `:root` once and never follows an override — which is why the elevation tokens are rebuilt in `cosmeticVars` instead. And a literal palette class (`text-zinc-300`, `TIER_STYLE`'s tier hues) follows nothing: on a dark ground that is merely off-palette, on a LIGHT cosmetic it is invisible, so it needs the `cos-light:` variant or a token.

14. **Every transient notification goes through `ToastHost`, which owns BOTH the timer and the tap target.** A notice that appears by itself and leaves by itself is dismiss-on-tap, without exception — the quick-chat bubbles (`pointer-events-none`, aged out on a timestamp) and the match-start countdown (`pointer-events-none` so the paddle stays drivable) are the only overheads that are not, and neither is a notification the player has to get rid of. A call site supplies `ttlMs` and `onDismiss` and nothing else; it must never arm its own `setTimeout`. Three of them used to, bare and uncancelled, so re-raising a notice inside its window let the first timer cut the second one short. **A timer must never be armed by an effect that depends on the dismiss callback.** App rebuilds every one of those on every render and re-renders once per animation frame while a ball is in play, so such an effect tears its timer down and re-arms it sixty times a second and never fires: that is how the achievement toast came to outlive the match that raised it, the winner overlay, and the menu after that — 15-30 seconds, and a different number every time, since it actually expired 4.5s after App last happened to re-render. `ToastItem` keys its effect on `[id, ttlMs]` alone and reads the callback through a ref, so the fix holds for every toast rather than one. The stack sits at `z-[75]` — above every `Sheet`, whose bands are 50/60/70 plus a stack index capped at four, so the top of the highest band is 74 and the toast clears it by one — because at `z-50` it was EARLIER in the DOM than the modals and the theme-unlock notice was painted over by the very Missions sheet that raised it; now that the notice expires on a timer, that would have made it invisible for good. It clears the screen's own top bar (`pt-safe-bar`) rather than burying the HUD row it is announcing something about. `toast-record-failed` is the one entry with no `ttlMs`, deliberately: it reports a state that is still unresolved and is cleared when the retry lands.

15. **A rule stated here is repeated in `.claude/skills/`, and both move together.** The skills
carry the *procedure* — which files a protocol change touches and in what order, which test
fails when a `playerId`-keyed table is not claimed, what the pre-match badge has to be told
about a new rule — while this file carries the reasoning. That duplication is deliberate and
it is the kind that drifts, exactly like the relay and the P2P replica: a skill that misstates
a touch-list is worse than no skill, because it is trusted. When a rule here moves,
`grep -rl "<identifier>" .claude/skills/` and fix it in the same commit, the same way a suite
asserting old behaviour is changed rather than left to be read later.

16. **A gesture commits on `pointerup` and never on `pointercancel`.** A cancel is the browser
saying it has taken the pointer — a notification shade, an edge swipe, a system gesture — so the
player never finished the thing being read as finished. `CourtCanvas.releasePointer(e, serve)`
and `useMenuSwipe`'s `release(e, settle)` are deliberately the same shape: one body, one boolean,
the decision snapshotted before the refs are cleared. Both once shared a handler between up and
cancel, and both fired on a shade pull — a serve nobody aimed, a page nobody turned. The
abort paths matter as much as the commit: `lostpointercapture`, `visibilitychange` and
`pagehide` all end a drag, because this app hands off to another browser through an `intent://`
URL and that produces no up and no cancel at all. And **capture is for a mouse**: a touch
pointer is already implicitly captured to the element it went down on, so `setPointerCapture`
TRANSFERS it and fires a bubbling `lostpointercapture` that aborts the drag being claimed. The
canvases capture on `pointerdown` safely only because they are `touch-none` surfaces with no
scroller and no inner button — never copy that onto a gesture over ordinary elements (§1).

## 10. Deployment

One Node service, one port, WebSockets on the same listener; **single-instance by design** (rooms live in process memory). Primary target: the **too-many-coins.com KVM via Dokploy** — Dokploy builds the `Dockerfile`, mounts a `phong-data` volume at `/data` (mandatory, or deploys wipe player data), and routes `phong.too-many-coins.com` through its Traefik with Let's Encrypt. The repo's `docker-compose.yml` (app + Caddy + optional coturn TURN relay, `--profile turn`) serves bare boxes without an existing proxy; the app mints time-limited TURN credentials from `TURN_STATIC_SECRET`. `render.yaml` remains as an alternative host. Env: `PORT`, `DATA_DIR`, `BUILD_ID` (optional — otherwise derived from the built client, see §5), `TURN_URL`, `TURN_STATIC_SECRET`. `SIGTERM` closes sockets (code 1001) and exits cleanly; deploys drop in-flight matches, and the players in them are returned to the menu. Full runbook: `DEPLOYMENT.md`; phone testing needs HTTPS (tunnel) — see `DEVELOPMENT.md`. **There is no current capacity figure here on purpose.** This line used to claim "10 concurrent matches with 0% loss" on the strength of `scripts/load-test.mjs`, which stopped running when the lobby handshake landed: it still awaits a `game_start` that no longer follows a join, having never sent `player_ready` or `start_match`, so it dies on the first pair. Nothing noticed, because `lint:suites` only covers `e2e-*.mjs`, `npm test` never touches it, `tsc` does not check `.mjs`, and CI never invokes it — a number nobody could reproduce sat in two documents for however long that was. The claim is gone until the script runs again; **a measurement in these files names the command that produces it, or it does not belong here.**

**A deploy must not cost anybody a rated match, and for a while it cost everybody one.** `shutdown()` closes every client, each close fires `vacateSeat`, and `abandoned` there is `bothSeated && inPlay && !matchOver && currentPlayerId` — true of every live duel. So a redeploy filed a real ranked LOSS against whichever seat's close handler ran first and a real ranked WIN to the other, spent the day's abandon forgiveness, and moved both players' career counters, for two people who did not leave. Measured with two phones mid-duel and both sockets held open across the signal: `played=1 won=1` against one and `played=1 won=0` against the other, before; nothing on either profile, after. A module-scope `shuttingDown`, set as the very first statement of `shutdown()` because every close after that point runs `vacateSeat`, drops the predicate through to the existing `persistDuelStreaks` branch — which is exactly the "this departure records no match" case — so both players keep their rally runs. There is still no draining: the `setTimeout(…, 5000)` caps the wait rather than waiting for anything, and a match in progress is still interrupted. It is simply no longer *charged*.

**Only `/assets` is served, and the reason is that `dist/` is not all client files.** The build emits `dist/server.cjs.map` beside them — 667KB with `sourcesContent: true` — and mounting `express.static` on the directory published it: a plain GET returned all 3,070 lines of `server.ts` plus `server/auth.ts`, `server/db.ts` and `server/room.ts` with the comments intact, which is the cookie HMAC construction, the exact placement of `requireActiveSession` and `seatStillHoldsAccount`, and every `matchKey` idempotency rule. `server.cjs` and `admin.cjs` were served beside it, and the `Dockerfile` carried all three into the runtime image, so this was live on every deployment path. `dist/` holds exactly `index.html`, `assets/` and those three outputs — there is no `public/` dir and `index.html` references nothing at the root — so naming the one directory the client needs is both the fix and the complete list; the rest now falls through to the SPA handler. The mount also finally does what the comment above it always claimed, since the hashed assets were being served `max-age=0` while only `index.html` got a header at all.

**The server says which database it opened, because the alternative is silence.** `DATA_DIR` falls back to a cwd-relative `./data`, and the `Dockerfile` both sets `DATA_DIR=/data` *and* `mkdir`s it — so a missing or misconfigured volume mount leaves a writable `/data` in the image layer and the process boots happily onto an ephemeral database, starting from zero accounts with no error and nothing naming the file. The boot line counts **accounts separately from rows**, and that distinction is the fix rather than a detail: the bot roster is re-seeded onto every fresh database, so a server that has just lost its volume reports eight players, and a naive `players === 0` check would never have fired on the one case it exists for. `/api/health` now **writes** as well — Docker's `HEALTHCHECK`, Render's `healthCheckPath`, Dokploy's probe and `scripts/e2e-run.mjs` all key on it, and it reported `ok` off process liveness alone, so a container with a corrupt file or a vanished volume was healthy while every write threw. A READ was the first answer and it did not deliver the promise: a `SELECT` succeeds on a filesystem that is full and on one remounted read-only, which are two of the three failures the probe names, so it went on answering 200 while every match, mission claim and profile write failed — which is the orchestrator's whole reason for asking. The write is **rate-limited to once per 10s** rather than run per request, because the route is unauthenticated and unmetered and one upsert per call would make the probe a write amplifier; a FAILING probe is deliberately re-run every time, since caching the failure would keep a recovered volume reported unhealthy for the rest of the window, and a server that cannot write has nothing to amplify.

**Every account, rating, level, achievement and match is one SQLite file, so `scripts/backup.mjs` is part of deploying.** `VACUUM INTO` takes a read transaction, so it is safe against a running server and folds the WAL into the copy — `cp phong.db` is not equivalent and can produce a file that opens fine and is missing the newest writes. What the documented one-liner it replaced lacked was everything around that: nothing scheduled it, nothing verified it, and it wrote the snapshot into `/data`, the same volume as the database, where a volume loss takes both and where on Render's 1GB disk the accumulating copies eventually take the live database down themselves. The script refuses to write inside `DATA_DIR`, opens the result and runs `PRAGMA integrity_check` before reporting success, prunes to `--keep`, and exits non-zero so a scheduler notices. It deliberately ships the file nowhere: where backups belong is a deployment decision, and **a backup that never leaves the host is not a backup**, because losing the host is the likeliest thing you are recovering from.
